# 서브에이전트 협업 워크플로우

## 코드 수정 시 원칙

코드 수정이 필요한 작업에서는 서브에이전트가 직접 코드를 수정하도록 위임한다.
main 에이전트는 분석/조율/결과 보고만 담당한다.

## Steps

### Phase 0: 영향 분석 (구현 전 필수)

기능 추가/수정/삭제 요청 시, 구현하기 전에 영향 범위를 먼저 분석하여 사용자에게 보고한다.
**사용자가 "진행해"라고 하기 전까지 구현하지 않는다.**

스킵 기준:
- 단일 파일 typo/포맷 수정
- 주석/문서만 변경
- 새 파일 추가 (기존 코드 수정 없음)
- 사용자가 "바로 해" 명시적 지시

### Phase 1: 기획
1. 기획 에이전트 호출
2. 기존 문서 확인 → 케이스 정의 작성/수정
3. 필요 시 비즈니스 로직/용어 문서 업데이트

### Phase 1.5: 기획 리뷰 (선택)
- 새 화면/기능 추가 시 → 적용
- 기존 케이스 1~2줄 수정 → 스킵
- 1회 리뷰 원칙 (무한 루프 방지)

### Phase 2: 디자인
1. 디자인 에이전트 호출 (기획 산출물 전달)
2. 케이스 기반 디자인 명세 구현
3. 토큰/컴포넌트 변경 시 영향 범위 보고

### Phase 2.5: 디자인 리뷰 (선택)
- 새 화면 추가 시 → 적용
- 기존 HTML 소규모 수정 → 스킵
- 1회 리뷰 원칙

### Phase 3: FE/BE 구현
1. 서브에이전트 병렬 호출 (FE/BE)
2. 디자인 명세 기반 FE 구현
3. API 구현
4. verification-loop 실행

### Phase 4: 리뷰
- 코드 리뷰 서브에이전트 호출
- 피드백 기반 수정 후 재리뷰는 하지 않는다 (1회 리뷰 원칙)

### Phase 5: 보고
- 사용자에게 변경 내용 + 영향 범위 보고

## 서브에이전트 호출 시 주의사항

- "직접 파일을 수정해줘"를 명시할 것
- 변경 대상 파일 경로와 컨텍스트를 충분히 제공할 것
- contextFiles로 경로만 전달, 인라인 코드 블록 금지
- FE/BE 간 인터페이스 변경 시 양쪽에 동일한 스펙 전달

## main 에이전트가 직접 수정해도 되는 경우

- steering/spec 등 설정 파일 수정
- 단일 파일의 간단한 수정 (한두 줄)
- 문서 단순 업데이트
