문제

테스트 데이터, 매번 손으로 만든다

“결제까지 마친 회원 데이터, 또 만들어야 해.”

서류합격 지원자, 결제를 마친 회원… 상황마다 다른 데이터가 필요합니다. 어떤 기능을 어떤 순서로 거쳐야 하는지 알아야 하고, 경우의 수가 많아 미리 만들 수도 없습니다.

핵심 원칙

DB를 직접 건드리지 않는다

❌ DB에 직접 INSERT

결제·차감 같은 실제 로직을 건너뜀 → 현실에 없는 데이터, 위험

✅ 실제 API로만 생성

실제 사용자와 똑같은 절차(검증·부수효과·정합성)를 거침 → 현실과 똑같은 데이터가 안전하게

실제로 쓰는 길로만
데이터를 만드니까
현실과 100% 일치

대표 시나리오 · 채용 서비스 예시

여러 서버를 넘나들며, 한 문장으로

“공고에 지원해서 서류합격 상태인 지원자 만들어줘”
구직자
1 회원가입 또는 로그인
2 메일 인증번호를 스크립트로 읽어 인증
3 운영 중인 공고 탐색 → 지원
기업
4 방금 들어온 지원 건을 서류합격으로 변경
결과 → 지원자 · 지원 공고 · 서류합격 상태까지 한 번에
이 시나리오가 보여주는 것

하나의 서버로 끝나지 않습니다. 구직자 서버와 기업 서버를 넘나들며 순서대로 실행합니다.

스크립트의 역할

메일 인증번호 읽기처럼 API만으로 막히는 중간 단계도 처리해 흐름이 끊기지 않습니다.

범용 AI 코딩 도구코드만 줄 뿐, 연결·실행은 각자사내 API 연결 + 실행 + 자산화
06 / 10
AI 활용

왜 굳이 AI인가

① 제품 안에서 — 핵심 동력

1말을 이해해 실행 — 요청을 이해해 필요한 API를 골라 순서대로 조합
2스스로 찾아 보완 — 부족한 정보는 API 목록·사내 문서에서 스스로
WHY — 매번 다른 요청을 이해하고 즉석에서 조합하는 판단은 규칙 자동화로는 불가능. AI만 할 수 있다.

② 개발 과정에서 — AI를 “팀처럼”

  • 기획 우선 — 기획 문서를 AI와 구조화 후 구현, 문서·코드 동기화
  • 규칙 내재화 — 코딩·보안·커밋 규칙을 AI가 늘 참조하도록 설정
  • 역할 분리 — 기획·백엔드·프론트·리뷰를 전문 역할로 나눠 병렬·교차 검토

→ 1인이 기획·백엔드·프론트·문서를 진행해 동작하는 프로토타입 완성

Appendix

어떻게 동작하나

준비 — 서버 연결 (1회)

  • 각 서버에 라이브러리 추가
  • 기동 시 API 목록(OpenAPI)을 자동 등록
  • DB 구조를 몰라도 됨, 재기동 시 최신으로 자동 갱신

사용 — 대화로 실행

  • 사용자가 말함 → AI가 필요한 API 선택
  • 사용자 브라우저에서 직접 호출 (내 로그인 세션 그대로 재사용)
  • 스텝 결과만 서버에 보고 → 저장·재개·히스토리
보안 — 시스템이 남의 인증 정보를 보관하지 않음. API 목록은 개발·스테이징에서만 전송.
