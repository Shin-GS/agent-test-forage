# 전체 히스토리 페이지

## URL

- `/history` — 히스토리 목록(목록형 페이지). 테이블 뷰로 실행 이력을 관리한다.
- `/history/:executionId` — 실행 결과 상세(상세/편집형 페이지). 아래 [실행 결과 상세](#실행-결과-상세-별도-페이지) 참조.

별도 **전체 화면 페이지**다. 채팅 레이아웃(사이드바 + 대화 영역 + 사이드 패널)을 벗어난다.

## 진입점

사이드바 하단 네비게이션의 **📊 히스토리**로 진입한다([README 네비게이션](../README.md#네비게이션) — `📋 📊 ⚙️` = 레시피 관리 / 히스토리 / 설정). 모든 라우트에서 상시 노출된다.

- 사이드 패널 히스토리 탭의 [전체 →]에서도 이 페이지로 이동한다([panel/history.md](../panel/history.md#패널-내-히스토리)).

## 데이터 소스

기존 실행 히스토리 조회 API를 **재사용**한다.

- `GET /api/v1/executions` — **본인 실행만** 반환(USER_ID 기준). 대화방 삭제와 무관하게 유지([db/execution.md 히스토리 독립성](../../db/execution.md#히스토리-독립성-historymd)).
- 커서 기반 무한 스크롤(`{ items, nextCursor, hasNext }`). 커서는 불투명 값(내부적으로 `EXECUTION.ID`).
- 필터 계약(서비스/상태/날짜/검색)은 [recipe/execution.md 히스토리 조회 API 계약](../recipe/execution.md#히스토리-조회-api-계약-get-executions) 참조.
- 사이드 패널 히스토리 탭과 **동일 API·동일 데이터 훅을 공유**하고 뷰(테이블 vs 목록)만 다르다([panel/history.md](../panel/history.md#패널-vs-전체-페이지-뷰-분리)).

## 화면 구성

**목록형 페이지**([상단 바 원칙](../common/page-layout.md))다. 제목 전용 헤더 없이 툴바(검색/필터)로 시작한다. 페이지 제목("실행 히스토리")은 숨김 `<h1>` + `document.title`로만 둔다.

```
┌──────────────────────────────────────────────────────────┐
│ [검색] [서비스 ▾] [상태 ▾] [기간 from~to] [초기화]         │  ← 툴바(sticky)
├──────────────────────────────────────────────────────────┤
│ 상태 | 레시피명 · 결과 요약        | 서비스 | 소요 | 시각   │
│ ──────────────────────────────────────────────────────── │
│ ✅ | 입사지원 · 지원번호 A-123    | 사람인 | 3.2s | 08/27 14:30 │
│ ✅ | 회원가입 · 가입 완료          | 사람인 | 1.8s | 08/27 14:25 │
│ ❌ | 재고확인 · 서버 응답 없음      | 쇼핑몰 | 0.5s | 08/27 10:00 │
│ ...                                                      │
├──────────────────────────────────────────────────────────┤
│ (무한 스크롤 — 하단 도달 시 다음 페이지 로드)              │
└──────────────────────────────────────────────────────────┘
```

## 검색 / 필터

모든 필터는 **다중 선택 + "빈 선택 = 전체"**(해당 축으로 거르지 않음)를 따른다. 필터 변경 시 커서를 리셋하고 처음부터 다시 조회한다(쿼리키에 필터 포함).

| 항목 | 방식 | 설명 |
|------|------|------|
| **검색** | 레시피명 텍스트 | 입력은 **디바운스** 후 질의. 서버는 `EXECUTION_RECIPE.RECIPE_NAME` 대상으로 매칭 |
| **서비스** | `apiSpecId` 다중 선택 | 실행이 **참조한 서비스**(`EXECUTION.API_SPEC_ID`) 기준. 빈 선택=전체 |

- **`apiSpecId=NULL` 실행 처리**(플랜/스펙 없는 실행): 서비스 필터를 적용하면 `API_SPEC_ID`가 NULL인 실행은 **제외**한다. 서비스 미선택(전체)일 때만 NULL 실행도 **포함**된다.
| **상태** | `ExecutionStatus` 다중 선택 | 성공(SUCCESS) / 실패(FAILED) / 중지(STOPPED) / 취소(CANCELLED). 빈 선택=전체 |
| **기간** | 날짜 범위(from~to) | FE는 날짜(`YYYY-MM-DD`) 선택. 서버는 `from 00:00:00 ~ to 23:59:59`(당일 포함, **서버 애플리케이션 타임존 기준** — 프로토타입 단일 서버, KST 가정)로 계약. 멀티 타임존 대응은 백로그 |

### 상태 필터 옵션 (확정)

상태 필터 옵션은 **완료 이력 4종**만 노출한다.

| 옵션 | enum | 아이콘 |
|------|------|--------|
| 성공 | `SUCCESS` | ✅ |
| 실패 | `FAILED` | ❌ |
| 중지 | `STOPPED` | ⏹️ |
| 취소 | `CANCELLED` | ⏸️ |

- **진행 중(`RUNNING`)·부분성공(`PARTIAL`)은 필터 옵션에서 제외**한다. 전체 히스토리는 "완료 이력 조회용"이므로 완료 건 위주로 본다.
- **`PARTIAL`(부분 성공)은 완료 건이므로 목록에는 노출**되나, 상태 필터 옵션은 성공/실패/중지/취소 4종만 제공한다(PARTIAL 전용 필터 옵션 없음).
- enum 정의: [db/execution.md 상태(STATUS)](../../db/execution.md#상태-status).

## URL 쿼리 동기화

검색어/필터 상태를 URL 쿼리에 반영한다. 새로고침·링크 공유 시 동일한 목록 상태가 복원된다. 목록형 페이지 공통 규칙([common/page-layout.md 목록 상태와 URL](../common/page-layout.md#목록-상태와-url-목록형-페이지-공통))을 따른다: URL이 상태의 단일 진실 소스이며, 필터 변경은 **replace**(히스토리 오염 방지), 검색어는 **디바운스 후 커밋**, enum(상태)은 허용값 화이트리스트로 파싱한다. 구현은 nuqs.

FE는 URL 쿼리키를 **API 파라미터명으로 매핑**해 `GET /api/v1/executions`를 호출한다(`q`→`keyword`, `spec`→`apiSpecId`). API 계약: [recipe/execution.md 히스토리 조회 API 계약](../recipe/execution.md#히스토리-조회-api-계약-get-executions).

| URL 쿼리 파라미터 | API 파라미터 | 대응 |
|--------------|--------------|------|
| `q` | `keyword` | 검색어(레시피명) |
| `spec` | `apiSpecId` | 서비스 다중(콤마 구분) |
| `status` | `status` | 상태 enum 다중(콤마 구분) |
| `from` / `to` | `from` / `to` | 날짜 범위(`YYYY-MM-DD`) |

- **커서는 URL에 넣지 않는다.** 필터가 바뀌면 커서를 리셋하므로, 쿼리키(`q`/`spec`/`status`/`from`/`to`)가 바뀔 때마다 처음부터 다시 로드한다.

## 정렬

**최신순 고정**(`startedAt DESC`). 사용자 정렬 컨트롤은 두지 않는다(커서 페이징 정렬 기준은 [db/execution.md 커서 페이징](../../db/execution.md#execution) 참조 — 내부적으로 `ID DESC`).

## 행 표기

| 요소 | 설명 |
|------|------|
| **상태 아이콘** | ✅ 성공 / ❌ 실패 / ⏹️ 중지 / ⏸️ 취소 |
| **레시피명** | `EXECUTION.TITLE`(또는 레시피명) |
| **결과 요약 1줄** | `RESULT_SUMMARY`. 넘치면 말줄임 |
| **서비스** | 실행 참조 서비스명(`API_SPEC_ID` 기준, 스펙 삭제 시 폴백) |
| **소요시간** | `DURATION_MS` 표기(없으면 생략) |
| **시각** | `STARTED_AT` |

- **실패/중지 행은 색으로 강조**한다(디자인 토큰 기반 — 하드코딩 금지, `--color-error` 등 [tokens.css](../../design/shared/tokens.css) 변수 사용).

## 실행 결과 상세 (별도 페이지)

행(또는 카드) 클릭 시 **별도 상세 페이지**(`/history/:executionId`)로 이동한다. 모달이 아니다.

### 왜 페이지인가 (모달 → 페이지 전환)

실행 결과 상세는 스텝별 원본 응답 JSON까지 들여다보는 **무거운 읽기 콘텐츠**이자, 링크로 공유할 가치가 있는 **독립적 목적지**다. 모달로 두면 딥링크 불가·새로고침 시 소실·뒤로가기 오작동·모바일 답답함이 생긴다. 페이지로 승격해 이를 해소한다.

프로젝트 상호작용 규칙(모달 vs 페이지 판단 기준)은 [common/ui-patterns.md](../common/ui-patterns.md) 정본을 따른다. 요약: **독립적으로 보는 결과물 = 페이지 / 작업 맥락 안 잠깐 참조 = 드로어·모달 / 짧은 결정·입력 = 모달.** 실행 결과 상세는 첫째에 해당한다(레시피 버전 미리보기는 편집 맥락 참조라 모달 유지).

### URL / 진입 / 복귀

- URL: `/history/:executionId` (상세형 별도 페이지). `executionId`가 URL의 단일 진실 소스다.
- 진입: 히스토리 목록 행 클릭 → **push** 네비게이션. 진입 시 **직전 목록 URL(필터 쿼리 포함)을 함께 전달**한다([common/page-layout.md 상세→목록 복귀](../common/page-layout.md#상세--목록-복귀-필터-유지)).
- 복귀: 상단 액션 바 **[← 목록으로]** 또는 **브라우저 뒤로가기** → 전달받은 목록 URL(필터 유지)로 복귀. 딥링크로 직접 진입해 전달값이 없으면 `/history`로 폴백.

### 화면 구성 (상세/편집형 페이지)

[상단 바 원칙](../common/page-layout.md)의 **상세/편집형**을 따른다. 제목 전용 헤더 없이 `PageShell` + `PageActionBar`로 구성한다. 페이지 제목은 숨김 `<h1>`("실행 히스토리 — {실행 제목}") + `document.title`로만 둔다.

```
┌──────────────────────────────────────────────────────────────────┐
│ [← 목록으로]  ✅ 회원가입 테스트 데이터 생성  [성공]                 │  ← 액션 바(sticky)
├──────────────────────────────────────────────────────────────────┤
│ ┌ 요약 ─────────────────────────────────────────────────────────┐ │
│ │ 서비스: 인증 API   모드: 자동   스텝 4/4 성공   소요 2.3초        │ │
│ │ 실행: 2026-09-15 14:32:07 (3시간 전)                            │ │
│ └───────────────────────────────────────────────────────────────┘ │
│ [실패 시] ⚠️ 3번 스텝 "결제 승인"에서 실패      [실패 지점으로 이동 ↓] │
│ ┌ 레시피 블록 ──────────────────────────────────────────────────┐ │
│ │ 회원가입        v2 기준·원본 현재 v5         [🔗 원본 레시피]     │ │  ← 레시피 헤더 + 원본 링크
│ │ ┌ 결과값 ─────────────────────────────────────────────────────┐ │ │
│ │ │ userId  10293 …                                             │ │ │
│ │ └─────────────────────────────────────────────────────────────┘ │ │
│ │ ┌ 실행 단계 ──────────────────────────────────────────────────┐ │ │
│ │ │ ✅ 1. …  ✅ 2. …  └[사용자 입력값 ▸][원본 응답 ▸](복사)        │ │ │
│ │ └─────────────────────────────────────────────────────────────┘ │ │
│ └───────────────────────────────────────────────────────────────┘ │
│  (플랜이면 위 "레시피 블록"이 레시피 수만큼 세로로 반복)            │
└──────────────────────────────────────────────────────────────────┘
```

레시피 제목·원본 링크·버전 안내는 **레시피 블록 헤더**에 둔다(액션 바가 아니라). 단일 실행(recipes 1개)도 동일하게 레시피 블록 헤더를 보여준다 — "단일=N=1 플랜" 원칙을 화면에서도 일관되게 유지한다.

#### 하나의 화면, 데이터에 따른 조건부 요소 (단일=N=1 플랜)

상세는 **화면이 하나**다. 성공/실패, 단일/플랜은 별도 화면이 아니라 **같은 화면에서 데이터에 따라 일부 요소만 조건부로 나타나는 변형**이다. BE도 단일 실행과 플랜을 동일 모델(`ExecutionResponse.recipes[]` 배열, 단일=길이 1)로 다루므로, FE도 `recipes[]`를 순회 렌더하는 **단일 컴포넌트**로 구현한다(단일을 "N=1 플랜"으로 취급).

| 조건 | 조건부 요소 |
|------|-------------|
| 상태가 실패/부분성공 | **실패 요약 배너 + 실패 지점 점프 + 실패 스텝 강조** 표시(성공이면 없음) |
| `recipes[]` 개수(단일 1 / 플랜 N) | **레시피 블록**을 개수만큼 세로 반복. 단일도 동일하게 1개 블록(레시피 헤더 포함) 표시 — 특수 분기 없음 |
| 원본 삭제/버전 상이 | **레시피 블록 헤더의** 링크 비활성/버전 배지(아래 [원본 레시피 링크 판정](#원본-레시피-링크-판정-레시피-블록-헤더)) |
| 로딩 / 404·권한없음 | 본문 자리에 **스켈레톤 / 빈 상태** |

- 골격(액션 바 + 요약 헤더 + 레시피 블록[결과값 + 실행 단계])은 **항상 동일**하고, 위 요소만 켜지고 꺼진다.
- 아래에서 "성공/실패/플랜/로딩/404"를 나눠 설명하는 것은 **같은 화면의 상태 예시**일 뿐, 별도 화면 정의가 아니다.

### 상단 액션 바 (`PageActionBar`)

스펙 상세(`/admin/specs/:id`)와 동일 구조로 통일한다.

| 슬롯 | 내용 |
|------|------|
| 뒤로가기 | `[← 목록으로]` (필터 유지 복귀) |
| 제목 | 실행 제목(`EXECUTION.TITLE`) + 상태 아이콘 |
| meta | 상태 배지(성공/실패/중지/취소/부분성공) |
| 우측 액션 | (없음) — **원본 레시피 링크는 레시피 블록 헤더로 이동**(아래 참조) |

액션 바에는 원본 레시피 링크를 두지 않는다. 실행은 레시피 여러 개(플랜)일 수 있어 "원본"이 하나로 특정되지 않기 때문이다. 원본 링크는 **각 레시피 블록 헤더**에 레시피별로 둔다.

### 레시피 블록 (레시피별 헤더 + 원본 링크)

본문은 `recipes[]`를 순회해 **레시피 블록**을 세로로 나열한다(단일=1개, 플랜=N개, 동일 규칙). 각 블록 헤더에 레시피명 + 원본 링크 + 버전 안내를 둔다.

```
{레시피명}        [버전 안내]                 [🔗 원본 레시피]
  결과값 …
  실행 단계 …
```

#### 원본 레시피 링크 판정 (레시피 블록 헤더)

상세 응답(`ExecutionRecipeView`)이 **레시피별로** 원본의 현재 상태를 파생 필드로 내린다(**엔티티 불변, response 계층에서 원본 조회** — [db/execution.md 상세 응답의 원본 레시피 상태](../../db/execution.md#상세-응답의-원본-레시피-상태-response-계층-파생-엔티티-불변)):

- `recipeDeleted` (boolean): 그 레시피의 원본이 삭제/부재면 true
- `recipeCurrentVersion` (int, nullable): 원본이 살아있으면 현재 버전, 아니면 null
- `recipeVersionNo` (기존): 실행 시점 버전

각 레시피 블록 헤더에서 위 필드로 링크·버전 안내를 표시한다:

| 원본 상태 | 링크 | 버전 안내 |
|-----------|------|-----------|
| 삭제/부재(`recipeDeleted=true`) | **비활성** "원본 삭제됨" | 없음 |
| 존재 + 버전 동일(`recipeVersionNo == recipeCurrentVersion`) | 활성 → `/recipes/:recipeId/edit` | 조용히 생략(중복 표기 안 함) |
| 존재 + 버전 상이(`recipeVersionNo != recipeCurrentVersion`) | 활성 → `/recipes/:recipeId/edit` (**항상 최신 원본**) | **"이 실행은 v{recipeVersionNo} 기준 · 원본 현재 v{recipeCurrentVersion}"** 배지/툴팁 |

- 링크는 **항상 원본의 최신 버전**(레시피 편집)으로 간다. 실행 당시 버전으로 바로 가는 링크는 두지 않는다 — 과거 버전은 레시피 편집의 **버전 기록 드로어**에서 본다([recipe/versioning.md](../recipe/versioning.md)).
- 상세 자체는 **실행 시점 스냅샷** 기준이라, 원본이 바뀌어도 이 페이지의 내용은 변하지 않는다. 버전 안내는 "원본이 그 사이 바뀌었음"을 알리는 맥락 표시일 뿐이다.
- **단일·플랜 동일 규칙**: 레시피 블록마다 자기 `recipeId` 기준으로 독립 판정한다. 특수 분기가 없다(단일=N=1 플랜).

### 데이터 소스 + 수평 권한

- 상세는 `GET /api/v1/executions/{id}`를 사용한다. 서버는 **본인(USER_ID) 소유 검증을 필수**로 수행하며, 타인 소유 `executionId` 접근 시 **404**를 반환한다(존재 여부 노출 방지).
- **404/삭제/권한 없음**(딥링크로 타인·삭제 실행 접근 등): 스펙 상세 페이지와 동일하게 **빈 상태 안내 + [목록으로]** 버튼을 노출한다(닫을 목록이 없는 페이지 특성상 토스트가 아니라 전용 화면으로 처리).
- 상세는 **실행 시점 스냅샷 기준**으로 렌더링([db/execution.md 레시피 스냅샷](../../db/execution.md#레시피-스냅샷-히스토리-재현)).

### 요약 헤더

넓은 페이지 폭을 활용해 핵심 지표를 상단 요약 영역에 모은다.

- **첫 지표는 단일/플랜에 따라 분기**한다:
  - **단일(recipes 1개)**: `서비스명`(`EXECUTION.API_SPEC_ID` 기준, 삭제 시 폴백). 레시피 1개 = 서비스 1개라 정확하다.
  - **플랜(recipes N개)**: `유형: 플랜 (N개 레시피)`. `EXECUTION.API_SPEC_ID`는 첫 레시피 것 하나뿐이라 요약 헤더에 대표 서비스만 넣으면 나머지 레시피 서비스가 가려져 오해를 준다. 따라서 요약 헤더에는 서비스를 넣지 않고 **유형+개수**를 보여주고, 서비스는 **각 레시피 블록**에서 파악한다.
- 공통 지표: 실행 모드(자동/직접) · **스텝 성공률(N/M)** · 소요시간(`DURATION_MS`). (모드·소요시간은 `EXECUTION` 단위 값이라 단일/플랜 무관하게 정확)
- **스텝 성공률 계산**: 분모 M = 실행된 모든 스텝 수(플랜이면 전 레시피의 스텝 합산). 분자 N = 상태가 `SUCCESS`인 스텝 수. `SKIPPED`(조건 미충족 건너뜀)는 N·M **모두에서 제외**한다(실행되지 않은 것으로 취급). `PENDING`(미실행)도 제외. 즉 "실제 실행된 스텝 중 성공 비율". FE가 `recipes[].steps[].status`를 순회해 계산한다(BE 별도 필드 없음).
- 실행 시각은 **절대시각 기본 + 상대시각 병기**(예: `2026-09-15 14:32:07 (3시간 전)`).

### 실패 스텝 강조 / 점프

- 실행이 실패/부분성공이면 요약 아래 **실패 요약 배너**를 노출한다: "**{N}번 스텝 "{스텝명}"에서 실패**"(가능하면 상태코드 병기). 실패가 여러 건이면 **가장 처음 실패한 스텝**(가장 앞 레시피의 가장 앞 실패 스텝) 기준.
- **플랜(다중 레시피)이면 레시피명을 함께 표기**한다: "**"{레시피명}" {N}번 스텝 "{스텝명}"에서 실패**"(어느 레시피인지 모호하지 않게). 단일 레시피는 레시피명 생략 가능.
- 배너의 **[실패 지점으로 이동]**은 해당 스텝으로 스크롤한다(스크롤 후 해당 스텝에 포커스). 실패 스텝 행은 색으로 강조한다(토큰 기반, `--color-error` 등).

### 실행 단계 / 결과값

- 헤더 지표는 위 요약 헤더로 이동했으므로, 본문은 **결과값 + 스텝별 결과**에 집중한다.
- 스텝별 결과: 상태 아이콘 + 요약 1줄. **펼침 시 원본 응답 JSON**(`EXECUTION_STEP.RESPONSE_JSON`)과 **사용자 입력값**(`USER_INPUT_JSON`) 확인.
- **복사**: 결과값과 스텝 원본 JSON에 복사 버튼을 둔다. 채팅 답변 복사와 동일한 상호작용(클립보드 복사 + "복사되었습니다" 토스트 + 잠깐 ✓ 피드백)을 공통 컴포넌트로 통일한다.
- 넓은 페이지에선 JSON 블록을 크게 보여준다(1단 레이아웃; 좌우 2단 분할은 백로그).

### 플랜(다중 레시피)

- `EXECUTION.TYPE=PLAN`은 `EXECUTION_RECIPE`가 여러 개다. 상세는 **레시피별로 세로로 나열**한다(레시피명 구분 + 각 레시피의 결과값/스텝). 기존 `ExecutionDetailView`의 `recipes[]` 순회 렌더 방식과 동일하다.
- 레시피별 탭/앵커 목차는 백로그(현재는 세로 나열로 통일).

### 로딩 상태

- 딥링크/새로고침으로 페이지에 직접 진입하면 목록 없이 상세부터 로드되므로, 데이터 도착 전 **로딩(스켈레톤/스피너)** 을 표시한다(스펙 상세 로딩 처리와 동일 결).

## 빈 상태 / 결과 없음

| 상황 | 표시 |
|------|------|
| **실행 이력 없음**(필터 없이 0건) | "아직 실행한 레시피가 없어요" 안내 + 채팅으로 유도 |
| **필터 결과 없음**(필터 적용 후 0건) | "조건에 맞는 실행 기록이 없어요" + [필터 초기화] 버튼 |

## 반응형

- 데스크톱: 테이블 뷰
- **Tablet 이하: 카드 폴백**(행을 세로 카드로 전환 — 상태/레시피명/요약/서비스/소요/시각을 카드 내부에 배치). 카드 클릭도 상세 페이지(`/history/:executionId`)로 이동하며, 상세 페이지 자체도 좁은 폭에서 요약/결과값/스텝을 세로로 스택한다.

## 백로그 (구현 안 함, 기록만)

| 항목 | 비고 |

| 플랜 히스토리 | 플랜 실행 구현 후. `EXECUTION(TYPE=PLAN)` + `EXECUTION_RECIPE` 펼침 표시 |

| CSV / JSON 내보내기 | 필터된 목록 내보내기 |
