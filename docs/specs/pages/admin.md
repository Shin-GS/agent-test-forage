# 관리자 페이지

## 개요

관리자 계정으로 로그인 시 추가로 접근 가능한 페이지.
관리자도 일반 사용자 기능(채팅, 레시피 실행)을 동시에 사용하므로, 별도 어드민 사이트가 아닌 기존 네비게이션의 연장선으로 제공.

> **작업 범위 표기**: 이 문서에서 **A(완료)**는 스펙 관리(목록/상세/비활성·활성·삭제) + RBAC 뼈대다. **B(현재 작업)**는 사용자 관리(`/admin/users`)로, RBAC 뼈대 위에서 사용자 CRUD·역할/상태 관리·비밀번호 지정을 구현한다. **별도**는 서비스 설명 편집이다.

## 네비게이션

사이드바 하단에 관리자 전용 아이콘 추가 (일반 사용자에게는 안 보임):

```
┌─────────┐
│ 대화 목록 │
│ ...     │
├─────────┤
│ 📋 📊 ⚙️ │  ← 공통 (레시피 관리, 히스토리, 설정)
│ ──────  │
│ 🖥️ 👥   │  ← 관리자 전용 (스펙 관리[A], 사용자 관리[B] — 둘 다 활성)
└─────────┘
```

- **노출 조건**: 관리자 전용 nav 아이콘은 `role == ADMIN`일 때만 렌더한다(일반 사용자에게는 아예 안 보임).
- **활성 범위**: 🖥️ 스펙 관리(A) + 👥 사용자 관리(B) 모두 활성이다. A에서 미표시(또는 비활성 placeholder)였던 👥 사용자 관리 nav를 B에서 활성화하고 `/admin/users`로 연결한다.
- `role`은 세션에서 도출한 값(`GET /api/v1/auth/me`)을 기준으로 판단한다. 클라이언트가 임의로 넣은 역할을 신뢰하지 않으며, nav 노출은 UX 게이팅일 뿐 실제 권한은 서버가 강제한다.

## RBAC 뼈대 (라우트 가드)

관리자 전용 페이지는 라우트 가드로 보호한다.

- **RequireAdmin 가드**: 관리자 전용 라우트(`/admin/**`)를 감싼다. `role != ADMIN`이면 `"/"`로 리다이렉트한다.
- `role` 판단 근거는 `GET /api/v1/auth/me` 응답. 비로그인(401)이면 로그인 플로우로, 로그인했으나 non-admin이면 `"/"`로 보낸다.
- 가드는 화면 접근 차단(UX)일 뿐이고, 데이터/변경은 **서버가 매 요청마다 역할을 재확인**해 강제한다(상세: [auth.md 역할 가드](../common/auth.md#역할-가드)).

## 스펙 관리 (A) (/admin/specs)

### 경로 전략 (조회 공용 / 관리 액션만 ADMIN)

스펙 API는 **admin prefix로 옮기지 않는다.** 스펙 **조회**(목록/상세)는 레시피 편집·사이드 패널의 서비스 드롭다운에서 일반 사용자도 사용하므로 공용(로그인 필수)으로 유지하고, **관리 액션(비활성/활성/삭제)에만 액션 단위로 ADMIN 역할을 체크**한다(비-admin은 403).

- 스펙 API 권한 매트릭스(정본)는 [auth.md 스펙 API 권한](../common/auth.md#스펙-api-권한-조회-공용--관리-액션만-admin--prefix-예외)에 있다. 표 중복(드리프트)을 피하기 위해 이 문서는 정본을 링크로 참조한다.
- 관리 액션은 `/api/v1/admin/**` prefix 규칙의 예외다(액션 단위 역할 체크). 근거·정합: [auth.md 역할 가드](../common/auth.md#역할-가드).
- `role`은 세션에서 도출한다(위조 금지).

### 조회 API 공용 vs 관리 화면 admin 전용 (의도된 비대칭)

- `GET /api/v1/specs/{id}`(상세 **조회 API**)는 **공용(로그인 필수)**이다. 레시피 편집·서비스 드롭다운 등 일반 사용자 기능이 스펙 상세를 읽어야 하기 때문이다.
- 반면 관리자 스펙 상세 **화면**(`/admin/specs/:id`)은 **RequireAdmin 가드**로 보호한다(non-admin은 `"/"`로 리다이렉트).
- 즉 "조회 API는 공용, 관리 화면은 admin 전용"이라는 비대칭은 **의도된 설계**다. API는 데이터 재사용을 위해 공용이고, 관리 화면은 관리 맥락(상태 변경 버튼 등)을 담으므로 admin 전용이다.

### INACTIVE 스펙 노출 정책 (확정)

- 공용 목록 API `GET /api/v1/specs`는 **ACTIVE만 반환**한다(INACTIVE 제외, 삭제된 스펙도 제외).
- 관리자 화면은 **전체(INACTIVE 포함)를 조회**한다. `GET /api/v1/specs?includeInactive=true` 형태로 조회하며, `includeInactive=true`는 **ADMIN만 허용**한다(비-admin이 지정 시 무시하거나 403 — 서버가 세션 역할로 강제).
- **알려진 사항(후속 처리)**: 공용 드롭다운이 ACTIVE만 노출하도록 바뀌므로, 레시피 편집에서 이미 **INACTIVE 스펙을 참조하던 경우** 그 스펙이 드롭다운에 안 나올 수 있다. "현재 선택된 INACTIVE 스펙을 편집 화면에서 표시"하는 예외 처리는 **이번 A 범위 밖(후속 작업)**이다.

### 목록 (`/admin/specs`)

```
┌──────────────────────────────────────────────────────────┐
│ 스펙 관리                                                │
├──────────────────────────────────────────────────────────┤
│ 서비스명   | baseUrl                  | 상태 | API 수 | 등록 시각        │
│ ──────────────────────────────────────────────────────────────────────── │
│ demo-shop  | https://shop.example.com | 🟢 ACTIVE   | 42개 | 방금 전       │
│ demo-pay   | https://pay.example.com  | ⚪ INACTIVE | 35개 | 1시간 전      │
│ demo-auth  | https://auth.example.com | 🟢 ACTIVE   | 28개 | 방금 전       │
└──────────────────────────────────────────────────────────┘
```

- 관리자 목록 화면은 **전체(INACTIVE 포함)를 조회**한다(`includeInactive=true`, ADMIN만 허용). 공용 목록 API는 ACTIVE만 반환하는 것과 구분된다(위 [INACTIVE 스펙 노출 정책](#inactive-스펙-노출-정책-확정) 참조).
- 삭제(소프트)된 스펙은 관리자 목록에서도 **제외**한다(삭제 = 없는 것으로 취급).
- 행 클릭 시 상세 페이지(`/admin/specs/:id`)로 이동한다.
- **INACTIVE 스펙은 목록에서 흐리게(dimmed)** 표시해 시각적으로 구분한다.
- **빈 상태**: 등록된 스펙이 하나도 없으면 "등록된 스펙이 없습니다" 안내를 표시한다(외부 서버가 client-spring 라이브러리로 등록하면 자동 노출됨을 함께 안내).

### 상세 (`/admin/specs/:id`, 별도 페이지)

엔드포인트가 많아 **모달이 아닌 별도 페이지**로 구성한다. 표시 항목:

| 항목 | 내용 | 이번(A) 범위 |
|------|------|--------------|
| 기본 정보 | 서비스명 / baseUrl / 상태 / 등록 시각 | 표시 |
| 서비스 설명 | description / domain / capabilities / notes | **읽기 전용 표시** (편집은 **별도**) |
| API 엔드포인트 목록 | method + path + summary + DEPRECATED 뱃지 | 표시 |
| 인증 프로필 | name + loginPageUrl | 표시 |
| 상태 관리 | [비활성화] / [활성화] 토글, [삭제] | A 범위 |

- **서비스 설명 편집은 별도 작업**이다(관리자 수정본이 yml보다 우선하는 정책은 [registration.md 우선순위 정책](../spec/registration.md#우선순위-정책) 참조). 이번 A에서는 읽기 전용으로만 노출한다.
- **읽기 전용 표시 값의 출처**: 관리자 수정본이 있으면 그것을, 없으면 yml 원본을 표시한다([registration.md 우선순위 정책](../spec/registration.md#우선순위-정책)의 관리자 우선 규칙을 그대로 따름).
- API 목록의 `DEPRECATED` 뱃지는 재등록 시 스펙에서 사라진 API를 나타낸다([registration.md 재등록 정합성](../spec/registration.md#재등록-정합성)).

### 스펙 상태 관리 (비활성/활성/삭제)

서버 URL 변경 등으로 좀비 스펙(구 baseUrl)이 남을 수 있어, 관리자가 직접 정리한다.

| 액션 | 동작 | 확인 |
|------|------|------|
| 비활성화 | STATUS = INACTIVE. AI 매칭/실행 대상에서 제외 | **ConfirmModal** |
| 활성화 | INACTIVE → ACTIVE 복귀 (관리자만) | 즉시(확인 불필요) |
| 삭제 | 소프트 삭제. 참조 레시피는 유효성 검증에서 경고 | **ConfirmModal** |

- **삭제/비활성은 되돌리기 부담이 있어 ConfirmModal로 한 번 확인**한다. 활성화는 복귀 성격이라 즉시 처리한다.
- 예: `shop-api.acme.com` → `shop.acme.com`으로 URL 변경 시, 구 URL 스펙은 더 이상 등록되지 않고 ACTIVE로 남으므로 → 관리자가 비활성/삭제로 정리 (자동 삭제 없음)
- INACTIVE/삭제된 스펙을 참조하는 레시피는 실행 전 유효성 검증에서 경고([registration.md 재등록 정합성](../spec/registration.md#재등록-정합성)).

## 사용자 관리 (B) (`/admin/users`)

계정은 셀프 회원가입 없이 **관리자가 이 화면에서 직접 생성/관리**한다([auth.md 계정 생성 정책](../common/auth.md#계정-생성-정책)). RBAC 뼈대(RequireAdmin 가드, 관리자 nav)는 A에서 완료되었고, B는 그 위에서 사용자 CRUD·역할/상태 관리·비밀번호 지정을 구현한다.

> **계정 삭제 정책(확정)**: 사용자 계정에는 **삭제 액션이 없다.** 계정 정리는 **비활성화(STATUS = INACTIVE)로 대체**한다. 하드 삭제·소프트 삭제 모두 이번 B 범위 밖(백로그)이다. 스펙 관리(A)가 소프트 삭제를 제공하는 것과 달리, 사용자 계정은 감사/이력 보존을 위해 삭제하지 않고 비활성 상태로만 관리한다.

### 경로 전략 (전부 ADMIN, admin prefix)

사용자 관리 API는 **`/api/v1/admin/users` prefix** 아래에 둔다. 이 prefix는 SecurityConfig가 ADMIN 역할을 강제하므로(미달 시 403), 개별 액션 역할 체크와 함께 이중 안전이 된다. 스펙 API(조회 공용 예외)와 달리 사용자 관리는 조회조차 관리자 전용이라 prefix 규칙을 그대로 따른다.

- 권한 매트릭스(정본)는 [auth.md 사용자 관리 API 권한](../common/auth.md#사용자-관리-api-권한-전부-admin--admin-prefix)에 있다. 표 중복(드리프트)을 피하기 위해 이 문서는 정본을 링크로 참조한다.
- `userId` / `role`은 세션에서 도출한다(위조 금지).

### API (5종)

| 메서드 | 경로 | 설명 | 실패 |
|--------|------|------|------|
| GET | `/api/v1/admin/users` | 목록. `?q=` 아이디 검색(부분 일치). 페이징 없음(단순 전체) | — |
| POST | `/api/v1/admin/users` | 생성 (username + password + name + role) | username 규칙 위반 **400**, 아이디 중복 **400**, 비밀번호 8자 미만 **400** |
| PATCH | `/api/v1/admin/users/{id}/role` | 역할 변경 (USER ↔ ADMIN) | 대상 없음 **404**, 자기보호/마지막 ADMIN 위반 **400** |
| PATCH | `/api/v1/admin/users/{id}/status` | 상태 변경 (ACTIVE ↔ INACTIVE) | 대상 없음 **404**, 자기보호/마지막 ADMIN 위반 **400** |
| PATCH | `/api/v1/admin/users/{id}/password` | 관리자가 새 비밀번호 직접 지정 | 대상 없음 **404**, 비밀번호 8자 미만 **400** |

- **목록 응답 항목**: `id`, `username`, `name`, `role`, `status`, `lastLoginAt`. 비밀번호 해시는 응답에 절대 포함하지 않는다.
- **username 검증(생성 시)**: `trim` 후 **3~50자**, **공백 불가**(앞뒤 공백 제거 후 내부 공백도 불가). 규칙 위반 시 **400**. 이미 존재하는 아이디면 중복 **400**(`UQ_APP_USER_USERNAME`).
- **name 검증(생성 시)**: **선택**(입력하지 않아도 됨). 입력 시 **100자 이하**.
- **비밀번호 정책**: 최소 8자. 저장은 bcrypt 해시(기존 `PasswordEncoder` 재사용). 비밀번호 변경은 **관리자가 새 비밀번호를 직접 지정**하는 방식이며, 임시 비밀번호 자동 발급이 아니다. 최초 로그인 시 변경 강제(`MUST_CHANGE_PASSWORD`)는 **백로그**다([db/user.md 확장 고려](../../db/user.md#확장-고려)).
- **대상 없음(404)**: 목록을 제외한 대상 지정 API(역할/상태/비밀번호 변경)에서 존재하지 않는 `userId`면 **404**로 응답한다.
- **비밀번호 변경과 세션(본인/타인)**: 비밀번호 변경은 **기존 세션에 영향을 주지 않는다.** 세션 재확인은 `STATUS`/`ROLE`만 검증하므로([auth.md 세션 상태/역할 재확인](../common/auth.md#세션-상태역할-재확인-비활성화역할-변경-반영)) 비밀번호를 바꿔도 재로그인이 강제되지 않는다(본인 비밀번호를 바꾼 경우도 동일).

### 자기 보호 + 마지막 ACTIVE ADMIN 보호 (서버 강제)

관리자 실수로 시스템에서 모든 관리자가 사라지는 것을 막기 위해, 서버가 아래를 매 요청 검증한다(위반 시 **400**).

| 규칙 | 대상 액션 | 허용/차단 |
|------|-----------|-----------|
| 본인 역할 강등(ADMIN→USER) | role 변경 | **차단** |
| 본인 비활성화(ACTIVE→INACTIVE) | status 변경 | **차단** |
| 마지막 ACTIVE ADMIN 강등 | role 변경 | **차단** (ACTIVE 상태 ADMIN이 1명뿐이면 그 계정 보호) |
| 마지막 ACTIVE ADMIN 비활성화 | status 변경 | **차단** |
| 본인 비밀번호 변경 | password 변경 | **허용** |

- "마지막 ACTIVE ADMIN"은 `ROLE=ADMIN AND STATUS=ACTIVE`인 계정 수가 1일 때 그 계정을 뜻한다. 이를 강등/비활성하면 활성 관리자가 0이 되므로 차단한다. 즉 **활성 관리자가 최소 1명 유지**되도록 보장한다.
- **INACTIVE 계정도 역할 변경은 가능**하다. 단 "마지막 ACTIVE ADMIN" 보호 카운트는 **`ROLE=ADMIN AND STATUS=ACTIVE`만 센다**(INACTIVE ADMIN은 카운트에서 제외). 따라서 INACTIVE 상태의 ADMIN을 강등해도 활성 관리자 수에 영향이 없다.
- 본인 계정 보호와 마지막 ADMIN 보호는 독립적으로 적용된다(본인이 아니어도 마지막 ACTIVE ADMIN이면 차단, 본인이면 마지막이 아니어도 강등/비활성 차단). 예: 유일한 ACTIVE ADMIN이 본인이면 자기보호와 마지막 ACTIVE ADMIN 보호가 **둘 다** 걸려 강등·비활성이 차단된다.
- 검증은 세션에서 도출한 `role`/본인 식별자 기준이다. 클라이언트가 보낸 값을 신뢰하지 않는다.

### 반영 시점 (역할/상태 변경)

- **계정 비활성화·역할 변경은 다음 요청부터 반영**된다(즉시 강제 로그아웃 없음). 인증 필터가 매 요청 시 세션의 `STATUS`/`ROLE`을 재확인하여, 비활성화 시 다음 요청에서 401(세션 폐기), 역할 변경 시 다음 요청부터 새 역할로 평가한다. 상세: [auth.md 세션 상태/역할 재확인](../common/auth.md#세션-상태역할-재확인-비활성화역할-변경-반영).
- 활성화(INACTIVE→ACTIVE)는 복귀 성격이라 즉시 반영(로그인 허용).

### 목록 화면

```
┌──────────────────────────────────────────────────────────────────┐
│ 사용자 관리                    [🔍 아이디 검색]   [+ 사용자 추가]  │
├──────────────────────────────────────────────────────────────────┤
│ 아이디 | 역할 | 상태 | 마지막 접속 | 액션                          │
│ ──────────────────────────────────────────────────────────────── │
│ admin (나) | 관리자 | 활성 | 10분 전 | [역할 변경*] [비활성*] [비번] │
│ user1      | 사용자 | 활성 | 1시간 전 | [역할 변경] [비활성] [비번]  │
│ user2      | 사용자 | 비활성 | 3일 전 | [역할 변경] [활성화] [비번]  │
└──────────────────────────────────────────────────────────────────┘
   * = 자기보호/마지막 ACTIVE ADMIN 보호로 비활성(disabled) + 툴팁
```

- **검색**: 상단 검색창으로 아이디 부분 일치 필터(`?q=`). 페이징은 없다(단순 전체 조회 + 클라이언트/서버 필터).
- **본인 행 표시**: 세션 사용자의 행에 "(나)" 배지를 표시한다.
- **위험 액션 게이팅(UX)**: 본인 계정의 역할 강등/비활성 버튼, 그리고 마지막 ACTIVE ADMIN의 역할 강등/비활성 버튼을 **비활성(disabled) + 이유 툴팁**으로 노출한다. 게이팅은 UX일 뿐이고 실제 차단은 서버가 400으로 강제한다(위 [자기 보호 + 마지막 ACTIVE ADMIN 보호](#자기-보호--마지막-active-admin-보호-서버-강제)).
- **빈/없음 상태**: 로그인한 관리자 본인이 최소 1명 존재하므로 목록이 완전히 비는 경우는 없다. 단, 검색 결과가 없을 때 "검색 결과가 없습니다" 안내를 표시한다.

### 액션 UI (모달 vs ConfirmModal)

| 액션 | UI | 입력 |
|------|-----|------|
| 사용자 추가 | **모달** | 아이디 + 비밀번호(8자+) + 이름 + 역할 |
| 비밀번호 변경 | **모달** | 새 비밀번호(8자+) |
| 역할 변경 (USER↔ADMIN) | **ConfirmModal** | 확인만 |
| 상태 변경 (활성/비활성) | **ConfirmModal** | 확인만 |

- 입력이 필요한 생성·비밀번호 지정은 폼 모달, 값 입력 없이 상태만 바꾸는 역할/상태 변경은 ConfirmModal로 오조작을 한 번 막는다.
