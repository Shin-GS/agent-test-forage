# 관리자 페이지

## 개요

관리자 계정으로 로그인 시 추가로 접근 가능한 페이지.
관리자도 일반 사용자 기능(채팅, 레시피 실행)을 동시에 사용하므로, 별도 어드민 사이트가 아닌 기존 네비게이션의 연장선으로 제공.

> **작업 범위 표기**: 이 문서에서 **A(현재 작업)**는 스펙 관리(목록/상세/비활성·활성·삭제) + RBAC 뼈대까지다. **B(다음 작업)**는 사용자 관리, **별도**는 서비스 설명 편집이다. B/별도 항목은 위치만 잡아두고 상세 설계는 하지 않는다.

## 네비게이션

사이드바 하단에 관리자 전용 아이콘 추가 (일반 사용자에게는 안 보임):

```
┌─────────┐
│ 대화 목록 │
│ ...     │
├─────────┤
│ 📋 📊 ⚙️ │  ← 공통 (레시피 관리, 히스토리, 설정)
│ ──────  │
│ 🖥️ 👥   │  ← 관리자 전용 (스펙 관리[A], 사용자 관리[B])
└─────────┘
```

- **노출 조건**: 관리자 전용 nav 아이콘은 `role == ADMIN`일 때만 렌더한다(일반 사용자에게는 아예 안 보임).
- **A 범위**: 🖥️ 스펙 관리만 활성. 👥 사용자 관리는 **B(다음 작업)**로, 이번엔 미표시(또는 비활성 placeholder)로 둔다.
- `role`은 세션에서 도출한 값(`GET /api/v1/auth/me`)을 기준으로 판단한다. 클라이언트가 임의로 넣은 역할을 신뢰하지 않으며, nav 노출은 UX 게이팅일 뿐 실제 권한은 서버가 강제한다.

## RBAC 뼈대 (라우트 가드)

관리자 전용 페이지는 라우트 가드로 보호한다.

- **RequireAdmin 가드**: 관리자 전용 라우트(`/admin/**`)를 감싼다. `role != ADMIN`이면 `"/"`로 리다이렉트한다.
- `role` 판단 근거는 `GET /api/v1/auth/me` 응답. 비로그인(401)이면 로그인 플로우로, 로그인했으나 non-admin이면 `"/"`로 보낸다.
- 가드는 화면 접근 차단(UX)일 뿐이고, 데이터/변경은 **서버가 매 요청마다 역할을 재확인**해 강제한다(상세: [auth.md 역할 가드](../common/auth.md#역할-가드)).

## 스펙 관리 (A) (/admin/specs)

### 경로 전략 (조회 공용 / 관리 액션만 ADMIN)

스펙 API는 **admin prefix로 옮기지 않는다.** 스펙 **조회**(목록/상세)는 레시피 편집·사이드 패널의 서비스 드롭다운에서 일반 사용자도 사용하므로 공용(로그인 필수)으로 유지하고, **관리 액션(비활성/활성/삭제)에만 액션 단위로 ADMIN 역할을 체크**한다(비-admin은 403).

- 스펙 API 권한 매트릭스(정본)는 [auth.md 스펙 API 권한](../common/auth.md#스펙-api-권한-조회-공용--관리-액션만-admin--prefix-예외)에 있다. 표 중복(드리프트)을 피하기 위해 이 문서는 정본을 링크로 참조한다.
- 관리 액션은 `/api/v1/admin/**` prefix 규칙의 예외다(액션 단위 역할 체크). 근거·정합: [auth.md 역할 가드](../common/auth.md#역할-가드).
- `role`은 세션에서 도출한다(위조 금지).

### 조회 API 공용 vs 관리 화면 admin 전용 (의도된 비대칭)

- `GET /api/v1/specs/{id}`(상세 **조회 API**)는 **공용(로그인 필수)**이다. 레시피 편집·서비스 드롭다운 등 일반 사용자 기능이 스펙 상세를 읽어야 하기 때문이다.
- 반면 관리자 스펙 상세 **화면**(`/admin/specs/:id`)은 **RequireAdmin 가드**로 보호한다(non-admin은 `"/"`로 리다이렉트).
- 즉 "조회 API는 공용, 관리 화면은 admin 전용"이라는 비대칭은 **의도된 설계**다. API는 데이터 재사용을 위해 공용이고, 관리 화면은 관리 맥락(상태 변경 버튼 등)을 담으므로 admin 전용이다.

### INACTIVE 스펙 노출 정책 (확정)

- 공용 목록 API `GET /api/v1/specs`는 **ACTIVE만 반환**한다(INACTIVE 제외, 삭제된 스펙도 제외).
- 관리자 화면은 **전체(INACTIVE 포함)를 조회**한다. `GET /api/v1/specs?includeInactive=true` 형태로 조회하며, `includeInactive=true`는 **ADMIN만 허용**한다(비-admin이 지정 시 무시하거나 403 — 서버가 세션 역할로 강제).
- **알려진 사항(후속 처리)**: 공용 드롭다운이 ACTIVE만 노출하도록 바뀌므로, 레시피 편집에서 이미 **INACTIVE 스펙을 참조하던 경우** 그 스펙이 드롭다운에 안 나올 수 있다. "현재 선택된 INACTIVE 스펙을 편집 화면에서 표시"하는 예외 처리는 **이번 A 범위 밖(후속 작업)**이다.

### 목록 (`/admin/specs`)

```
┌──────────────────────────────────────────────────────────┐
│ 스펙 관리                                                │
├──────────────────────────────────────────────────────────┤
│ 서비스명   | baseUrl                  | 상태 | API 수 | 등록 시각        │
│ ──────────────────────────────────────────────────────────────────────── │
│ demo-shop  | https://shop.example.com | 🟢 ACTIVE   | 42개 | 방금 전       │
│ demo-pay   | https://pay.example.com  | ⚪ INACTIVE | 35개 | 1시간 전      │
│ demo-auth  | https://auth.example.com | 🟢 ACTIVE   | 28개 | 방금 전       │
└──────────────────────────────────────────────────────────┘
```

- 관리자 목록 화면은 **전체(INACTIVE 포함)를 조회**한다(`includeInactive=true`, ADMIN만 허용). 공용 목록 API는 ACTIVE만 반환하는 것과 구분된다(위 [INACTIVE 스펙 노출 정책](#inactive-스펙-노출-정책-확정) 참조).
- 삭제(소프트)된 스펙은 관리자 목록에서도 **제외**한다(삭제 = 없는 것으로 취급).
- 행 클릭 시 상세 페이지(`/admin/specs/:id`)로 이동한다.
- **INACTIVE 스펙은 목록에서 흐리게(dimmed)** 표시해 시각적으로 구분한다.
- **빈 상태**: 등록된 스펙이 하나도 없으면 "등록된 스펙이 없습니다" 안내를 표시한다(외부 서버가 client-spring 라이브러리로 등록하면 자동 노출됨을 함께 안내).

### 상세 (`/admin/specs/:id`, 별도 페이지)

엔드포인트가 많아 **모달이 아닌 별도 페이지**로 구성한다. 표시 항목:

| 항목 | 내용 | 이번(A) 범위 |
|------|------|--------------|
| 기본 정보 | 서비스명 / baseUrl / 상태 / 등록 시각 | 표시 |
| 서비스 설명 | description / domain / capabilities / notes | **읽기 전용 표시** (편집은 **별도**) |
| API 엔드포인트 목록 | method + path + summary + DEPRECATED 뱃지 | 표시 |
| 인증 프로필 | name + loginPageUrl | 표시 |
| 상태 관리 | [비활성화] / [활성화] 토글, [삭제] | A 범위 |

- **서비스 설명 편집은 별도 작업**이다(관리자 수정본이 yml보다 우선하는 정책은 [registration.md 우선순위 정책](../spec/registration.md#우선순위-정책) 참조). 이번 A에서는 읽기 전용으로만 노출한다.
- **읽기 전용 표시 값의 출처**: 관리자 수정본이 있으면 그것을, 없으면 yml 원본을 표시한다([registration.md 우선순위 정책](../spec/registration.md#우선순위-정책)의 관리자 우선 규칙을 그대로 따름).
- API 목록의 `DEPRECATED` 뱃지는 재등록 시 스펙에서 사라진 API를 나타낸다([registration.md 재등록 정합성](../spec/registration.md#재등록-정합성)).

### 스펙 상태 관리 (비활성/활성/삭제)

서버 URL 변경 등으로 좀비 스펙(구 baseUrl)이 남을 수 있어, 관리자가 직접 정리한다.

| 액션 | 동작 | 확인 |
|------|------|------|
| 비활성화 | STATUS = INACTIVE. AI 매칭/실행 대상에서 제외 | **ConfirmModal** |
| 활성화 | INACTIVE → ACTIVE 복귀 (관리자만) | 즉시(확인 불필요) |
| 삭제 | 소프트 삭제. 참조 레시피는 유효성 검증에서 경고 | **ConfirmModal** |

- **삭제/비활성은 되돌리기 부담이 있어 ConfirmModal로 한 번 확인**한다. 활성화는 복귀 성격이라 즉시 처리한다.
- 예: `shop-api.acme.com` → `shop.acme.com`으로 URL 변경 시, 구 URL 스펙은 더 이상 등록되지 않고 ACTIVE로 남으므로 → 관리자가 비활성/삭제로 정리 (자동 삭제 없음)
- INACTIVE/삭제된 스펙을 참조하는 레시피는 실행 전 유효성 검증에서 경고([registration.md 재등록 정합성](../spec/registration.md#재등록-정합성)).

## 사용자 관리 [B — 다음 작업] (`/admin/users`)

> **이 섹션은 B(다음 작업)다.** 현재 A 범위(스펙 관리 + RBAC 뼈대)에는 포함되지 않는다. 아래 내용은 위치 확보용 초안이며, 상세 설계·구현은 B에서 진행한다. 사이드바 👥 사용자 관리 nav는 A에서 미표시(또는 비활성 placeholder)로 둔다.

### 목록

```
┌──────────────────────────────────────────────────────────┐
│ 사용자 관리                              [+ 사용자 추가]  │
├──────────────────────────────────────────────────────────┤
│ 아이디 | 역할 | 생성일 | 마지막 접속 | 상태               │
│ ──────────────────────────────────────────────────────── │
│ admin   | 관리자 | 2026-08-01 | 10분 전 | 활성            │
│ user1   | 사용자 | 2026-08-15 | 1시간 전 | 활성           │
│ user2   | 사용자 | 2026-08-20 | 3일 전 | 비활성           │
└──────────────────────────────────────────────────────────┘
```

### 기능

| 기능 | 설명 |
|------|------|
| 계정 생성 | 아이디 + 비밀번호 + 역할(일반 사용자/관리자) 직접 지정. 셀프 회원가입은 없고, 계정은 관리자가 이 화면에서 생성한다 |
| 역할 변경 | 사용자 ↔ 관리자 |
| 계정 비활성화/활성화 | 로그인 차단/허용 |
| 비밀번호 변경 | 관리자가 새 비밀번호를 직접 지정 |

- **계정 비활성화·역할 변경은 다음 요청부터 반영**된다(즉시 강제 로그아웃 없음). 인증 필터가 매 요청 시 세션의 `STATUS`/`ROLE`을 재확인하여, 비활성화 시 다음 요청에서 401(세션 폐기), 역할 변경 시 다음 요청부터 새 역할로 평가한다. 상세: [auth.md 세션 상태/역할 재확인](../common/auth.md#세션-상태역할-재확인-비활성화역할-변경-반영).

## 공통 레시피 관리

별도 관리 페이지 불필요. 기존 레시피 편집 페이지(`/recipes`)에서:
- 관리자만 "공개 범위: 공통" 선택 가능
- 일반 사용자는 "개인"만 선택 가능
