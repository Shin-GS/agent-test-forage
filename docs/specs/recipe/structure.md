# 레시피 구조

## 소유 구분

- **공통 레시피** — 관리자가 생성, 모든 사용자에게 노출
- **개인 레시피** — 본인만 사용

## 메타 정보

| 항목 | 설명 | 필수 |
|------|------|------|
| 레시피명 | 식별 + AI 매칭용 | ✅ |
| 설명 | AI 의도 매칭에 활용 | ✅ |
| 대상 서비스 | 분류용 단일 라벨(`apiSpecId` 1개). 목록 필터/AI 매칭/분류용 (단일 선택) | ✅ |
| 태그 | 분류/검색/필터용 (복수 입력) | 선택 |
| 공개 범위 | 공통 / 개인 | ✅ |
| 사용자 입력 변수 | 실행 시 사용자에게 물어볼 데이터 | 선택 |
| 스텝 목록 | 실행할 작업 순서 | ✅ |

### 서비스의 두 층위 (실행 vs 분류)

레시피는 서비스 개념을 두 층위로 갖는다. 둘은 **독립적**이다.

| 층위 | 대상 | 설명 |
|------|------|------|
| **실행 층위** | 스텝별 `apiSpecId`/`endpointId` | API 스텝은 **여러 서비스의 API를 호출 가능**(스텝마다 지정, 멀티 서비스 허용) |
| **분류 층위** | 메타의 대상 서비스(`apiSpecId` 1개) | 태그 같은 **단일 분류 라벨**. 목록 필터/AI 매칭/분류용 |

- 스텝이 다른 서비스의 API를 호출하더라도 **메타 대상 서비스는 바뀌지 않는다**(분류 라벨일 뿐).
- 목록의 서비스 필터는 **메타 대상 서비스 기준**으로 거른다(스텝의 내부 호출 서비스로 필터하지 않음). [recipe-editor.md 목록 필터](../pages/recipe-editor.md#검색--필터--정렬) 참조.

#### 멀티 서비스 실행 규칙 (확정)

API 스텝은 **자신의 `apiSpecId`가 가리키는 서비스의 endpoint를 호출**한다. 한 레시피 안의 스텝들이 서로 다른 서비스를 가리켜도 정상이다(멀티 서비스).

- **스텝별 서비스 해석**: 각 API 스텝은 `apiSpecId`(대상 서비스) + `endpointId`(그 서비스의 endpoint)를 1급 필드로 가진다. 실행 시 `apiSpecId`의 `baseUrl` + endpoint의 `method`/`path`를 조합해 요청을 만든다(스텝별 baseUrl 해석: [execution.md 스텝별 baseUrl/endpoint 해석](execution.md#스텝별-baseurlendpoint-해석-멀티-서비스)).
- **path 표기**: endpoint 원본 `path`(예: `/seats/{seatId}/bookings`)를 그대로 보존하고, 실행 시 `pathParams`로 경로 변수를 치환한다. 원본 path를 미리 치환해 저장하지 않는다.
- **검증(스텝 단위 경계)**: 저장 시 [RecipeValidator]가 각 API 스텝의 **`apiSpecId` 기준으로 `endpointId`의 소속·존재·상태(ACTIVE)** 를 검증한다. 스텝이 다른 서비스를 가리키는 것은 정상 허용하되, endpoint가 없거나 그 서비스 소속이 아니거나 비활성(INACTIVE/DEPRECATED)이면 **경고**한다(즉시 실행 실패 방지). 전역 조회로 존재만 확인하던 무경계 상태를 스텝의 `apiSpecId`로 경계 지어 검증한다. ([authoring.md 유효성 검증](authoring.md#유효성-검증))
- **endpointId 필수 / 미완성 스텝 처리**: API 스텝은 저장 시 `endpointId`가 **필수**다(기존 규칙 유지). `apiSpecId`(서비스)만 고르고 `endpointId`(API)를 아직 안 고른 스텝은 **미완성**으로 보아 [RecipeValidator]가 걸러 `VALIDATION_STATUS=INVALID`로 저장한다(실행 진입 전 경고). 즉 `apiSpecId`는 상속으로 채워질 수 있어도, `endpointId`는 사용자가 명시 선택해야 한다. `endpointId` 없는 스텝은 실행 스냅샷 `resolvedSteps` 항목을 만들 수 없으므로 실행 대상이 될 수 없다.
- **분류 층위 불변**: 스텝의 `apiSpecId`가 메타 대상 서비스와 달라도 메타 대상 서비스(분류 라벨)는 바뀌지 않는다.

#### 스텝 서비스 지정 모델 (상속 UX + 저장 시 명시 확정) — 확정

편집 UX는 "상속"으로 편하게, 저장 데이터는 "명시"로 엄격하게 간다. 두 단계를 분리한다.

| 단계 | 규칙 |
|------|------|
| **편집 중** | API 스텝의 대상 서비스(`apiSpecId`) **미선택을 허용**한다. 미선택 상태는 "레시피 대상 서비스([메타의 대상 서비스](#메타-정보))를 상속"으로 간주하고, 편집 UI에 상속받는 서비스를 **표시**한다(예: "상속: 사람인"). |
| **저장 시** | 미선택(상속) 스텝은 저장 요청 직렬화 시점에 **FE가 레시피 대상 `apiSpecId`로 확정해 채워 전송**한다. 즉 서버로 올라가는 STEPS_JSON에는 `apiSpecId` 없는 API 스텝이 남지 않는다. |

- **불변식**: **`endpointId`가 있는 API 스텝은 저장 후 항상 `apiSpecId`를 가진다.** `apiSpecId` 미지정(상속) 상태는 **편집 중에만** 존재하고, 저장을 통과하면 사라진다. 즉 **저장된 STEPS_JSON에는 `apiSpecId` 없는 API 스텝이 존재하지 않는다.**
- **확정 주체 = FE / 신뢰 경계 = 서버**: `apiSpecId` 확정은 **FE가 저장 요청을 직렬화할 때** 수행하고(사용자가 스텝 서비스 미선택이면 레시피 대상 `apiSpecId`를 채워 전송), 서버는 STEPS_JSON을 통짜 저장한다(파싱은 검증용만). 다만 FE 값을 그대로 신뢰하지 않고, 서버의 [RecipeValidator]가 스텝 `apiSpecId` 기준으로 `endpointId`의 소속·존재·ACTIVE를 검증해 신뢰 경계를 확보한다(잘못된 `apiSpecId`는 검증에서 걸러진다).
- **다른 서비스 지정**: 스텝에서 레시피 대상과 다른 서비스를 명시 선택하면 그대로 기록한다(상속받지 않음). 멀티 서비스는 이 명시 선택으로 구성된다.
- **구 데이터 처리(정식 구현)**: 배포 전이라 하위호환 부담이 없으므로, `apiSpecId` 없는 구 스텝 데이터는 **로드 시 조용한 폴백에 의존하지 않고** 일회성 마이그레이션으로 `apiSpecId`를 확정 기록한다(`endpointId`로 소속 서비스 역산). 보정 대상은 `RECIPE.STEPS_JSON` + `RECIPE_VERSION.SNAPSHOT_JSON` 내부 stepsJson이며, 실행 히스토리 스냅샷은 "그때 그대로" 원칙으로 보정하지 않는다. 상세: [db/recipe.md apiSpecId 역산 마이그레이션](../../db/recipe.md#apispecid-역산-마이그레이션-일회성).
- **실행 시 못 찾음**: 실행 시 스텝의 `apiSpecId`가 가리키는 서비스(스펙)를 찾지 못하면(삭제/비활성) `DEFAULT_BASE_URL` 같은 조용한 폴백을 하지 않고 **그 스텝을 명확히 실패 처리**한다([execution.md 스텝 서비스 못 찾음](execution.md#스텝-서비스스펙-못-찾음-실패-처리)).

## 스텝 타입

프로토타입에서 **실제 실행 가능한 스텝 타입은 아래 3종**이다.

| 타입 | 역할 |
|------|------|
| **API** | 외부 서버 API 호출 |
| **스크립트** | JavaScript 실행 (데이터 가공, 조건 판단) |
| **레시피** | 다른 레시피를 서브레시피로 호출 |

> **사용자 입력은 별도 스텝 타입이 아니다.** 프로토타입에서는 레시피 메타의 ② [사용자 입력 변수](#사용자-입력-변수-실행-전-수집)로 대체하며, 실행 시작 직전 액션 피커로 **1회 수집**한다. 실행 중 동적으로 입력을 요청하는 "사용자 입력 스텝"은 **추후 확장** 대상이다.

### API 타입

| 항목 | 설명 |
|------|------|
| 스텝명 | 식별용 (내부 식별) |
| 표시명 (선택) | 비개발자용 스텝 표기. 비우면 자동 폴백 (아래 [표시명 폴백 체인](#표시명label-폴백-체인)) |
| 대상 서비스 (`apiSpecId`) | **이 스텝이 호출할 서비스**(스펙). 스텝별로 지정 → 레시피 내 스텝마다 다른 서비스 가능(멀티 서비스). 스펙 목록에서 선택 |
| API (`endpointId`) | 위 서비스에 속한 endpoint 선택(method + path). `apiSpecId`와 함께 스텝 JSON의 1급 필드로 저장 |
| 요청 필드 매핑 | 경로/쿼리 파라미터·바디 필드에 값 매핑. 스키마에서 자동 나열([authoring.md ③](authoring.md#api-타입--요청-필드-매핑)) |
| 요청 헤더 매핑 | 요청 헤더에 값 매핑. 실행 시 실제 요청 헤더로 주입(2단계). 스펙의 헤더 정의를 자동 제시 |
| Body | 요청 본문 (변수 바인딩 가능) |
| Body 생성 전략 | FIXED / AI_GENERATE / AI_FILL |
| AI 힌트 | AI 컨텍스트 (AI 전략 사용 시) |
| Extract | 응답에서 추출할 변수 (JSONPath) |
| 레시피별 기본값 | 각 매핑 필드/헤더에 이 레시피에서의 기본값. 실행 시 `사용자 실행 입력 > 레시피별 기본값` 우선순위 |
| 조건 (선택) | 실행 조건. 불만족 시 스킵 |

- 요청 필드/헤더 매핑의 **값 소스는 4종 공통**(이전 스텝 결과 / 사용자 입력 / 직접 입력 / AI 생성)이며, 값 소스·기본값·헤더 주입 규칙은 [authoring.md](authoring.md#api-타입--요청-필드-매핑)·[execution.md 요청 헤더 주입](execution.md#요청-헤더-주입-2단계)을 정본으로 한다.

#### 사용자 입력 변수 (실행 전 수집) — 프로토타입 방식

프로토타입 액션 피커는 **레시피 메타의 `사용자 입력 변수`를 실행 시작 직전 1회 수집**한다. 트리거·값 부족·재개 규칙은 [execution.md 사용자 입력 수집](execution.md#사용자-입력-수집-액션-피커) 참조.

- **작성 규칙**: API/스크립트 스텝이 참조하는 `{{userInput.X}}` 키는 반드시 레시피 메타의 `사용자 입력 변수`에도 선언해야 한다. 선언되지 않은 값은 액션 피커로 물을 수 없고, 실행 시 비면 실패 처리된다.

## 조건 분기

각 스텝에 `condition` 필드를 붙여 조건부 실행/스킵 가능. 1차원 순차 구조 유지.

```json
{
  "name": "회원가입",
  "type": "recipe",
  "recipeId": 123,
  "condition": "{{Step0.statusCode}} === 401"
}
```

- 조건 만족 → 스텝 실행
- 조건 불만족 → 스킵하고 다음 스텝으로

## 스텝 간 데이터 전달

| 스코프 | 접근 방식 | 설명 |
|--------|-----------|------|
| 사용자 입력 | `{{userInput.변수명}}` | 액션 피커에서 받은 값 |
| 이전 스텝 추출값 | `{{변수명}}` | extract로 뽑은 값 |
| 이전 스텝 전체 응답 | `{{Step0}}`, `{{Step1}}` | 원시 응답 전체 |

## 스크립트에서의 변수 접근

```javascript
function execute(context) {
  const memberId = context.memberId;       // extract된 값
  const rawResponse = context.Step0;       // 0번 스텝 전체 응답
  const userInput = context.userInput;     // 사용자 입력값
  return { processedData: "..." };         // 다음 스텝에서 참조 가능
}
```

## 표시명(label) 폴백 체인

비개발자가 결과를 이해하도록, 스텝과 결과 값에는 사람말 표시명을 붙인다. 표시명은 **선택 입력**이고, 비우면 아래 순서로 자동 폴백해 **어떤 경우에도 표기가 깨지지 않는다**.

| 대상 | 폴백 우선순위 |
|------|--------------|
| 스텝 표시명 | (1) 레시피 스텝에 등록한 표시명 → (2) 엔드포인트 `summary`(스펙 원천, 한글 가능) → (3) `method + path` |
| 결과키 표시명 | (1) 결과 정의(④)에 등록한 `label` → (2) 없으면 원본 key 그대로(`orderId` 등) |

### 원칙

- 표시명 입력은 선택 필드. 비우면 자동(스텝=summary / 결과키=원본 key)으로 폴백한다.
- 중첩/배열 key(`items[0].price`)는 `label`이 없으면 **key 경로를 그대로** 표시하고, 값이 없거나 null이면 **"값 없음"**으로 표시한다. **이 "key 경로 그대로 / 값 없음" 규칙은 결과키 표기에만 해당한다** — 스텝 표시명은 폴백 체인 (3)단계(`method + path`)까지 항상 값이 존재하므로 "값 없음"이 발생하지 않는다.
- 채팅 요약은 사람말(content/템플릿/AI 요약), 상세·히스토리는 기술 원문(key/method+path)을 허용하는 [기존 이원화](../common/messaging.md#content-vs-payloadjson-필드-이원화)를 유지한다. 표시명은 사람말 쪽을 보강하는 값이다.

### 스냅샷 포함

- 스텝 표시명과 결과 정의 `label`은 **레시피 스냅샷([RECIPE_VERSION](../../db/recipe.md#recipe_version))에 포함**된다.
- 히스토리 재현 시 그때 그 이름이 유지되도록, 실행 시점의 표시명을 함께 기록한다(스펙 `summary`가 이후 바뀌어도 과거 실행 표기는 흔들리지 않음).
- **폴백 결과도 실행 시점에 고정**: 스텝에 표시명(label)이 없어 summary(또는 method+path)로 폴백된 경우에도, 서버가 **실행 시점에 폴백 체인으로 확정한 사람말 이름을 PROGRESS 파트 payload의 `steps[].name`에 저장**한다. 따라서 히스토리 재현·새로고침 복원 시에도 "조회 당시 summary"가 아니라 **그때 그 실행 시점의 이름**이 그대로 표시된다(스펙 `summary`가 이후 변경돼도 과거 표기 불변). PROGRESS `steps[].name` 저장: [messaging.md PROGRESS 스키마](../common/messaging.md#progress-실행-진행-블록)
