# 레시피 실행 플로우

## 실행 진입

```
사용자 발화 (채팅)
    │
    ▼
AI 의도 분석 → 레시피 매칭 (참조 태그 있으면 우선 참조)
    │
    ├─ 매칭됨 → execution_mode 카드 (레시피명 + 설명 + 필요한 값 목록) + 실행 모드 선택
    │            ├─ [바로 실행] → 발화/기본값으로 즉시 진행
    │            └─ [값 확인 후 실행] → 액션 피커로 전체 값 확인·수정 후 진행
    │
    └─ 매칭 안 됨 → 안내 메시지
```

## 실행 모드

레시피 실행 시 **execution_mode 카드**로 "무엇을 실행하는지, 어떤 값이 필요한지"를 함께 보여주고 모드를 선택하게 한다. 버튼만 노출하지 않는다.

```
AI: 📋 입사지원 (사람인)
    사람인 채용공고에 이력서를 제출합니다.

    필요한 값:
    🗣️ 회사명       "네이버"        (필수)
    📌 직무          "백엔드"        (기본값)
    ✏️ 지원 메모     (입력 필요)      (필수)

    [바로 실행] [값 확인 후 실행]
```

- **레시피명 + 한줄 설명**: 무엇을 실행하는지 표시
- **필요한 값 목록**: 각 입력 변수의 라벨 / 현재값 / 값 출처(🗣️ 발화 · 📌 기본값 · ✏️ 미입력) / 필수 여부. 채워진 값은 값+출처, 미충족 필수값은 "(입력 필요)"
- 카드 필드 구조(`recipeName`/`description`/`inputVariables`/`buttons`): [messaging.md execution_mode 카드 상세](../common/messaging.md#execution_mode-카드-상세)

| 모드 (버튼) | 동작 |
|------|------|
| **바로 실행** | 발화/기본값으로 즉시 진행. 판단 불가능한 것(미충족 필수값)만 중간에 물어봄 |
| **값 확인 후 실행** | 액션 피커로 전체 값을 확인·수정한 뒤 진행 |

사용자가 발화에서 이미 값을 지정한 경우("네이버 백엔드로 입사지원 해줘") 해당 값은 자동 반영되어 카드의 "필요한 값"에 🗣️ 발화 출처로 표시된다.

## 사용자 입력 수집 (액션 피커)

### 프로토타입 스코프

레시피의 **사용자 입력 변수**(메타에 정의, `{{userInput.*}}`로 참조)를 실행 전 액션 피커로 한 번에 수집한다.
실행 중간에 스텝별로 값을 요청하는 **동적 입력(USER_INPUT 스텝)은 추후 확장**이다. ([structure.md](structure.md#사용자-입력-타입) 방침과 정합)

즉 프로토타입에서 액션 피커는 **레시피 실행 시작 직전(pre-run) 1회** 뜬다. 실행 도중에는 뜨지 않는다.

### 액션 피커 트리거 (확정)

| # | 트리거 | 액션 피커 노출 여부 |
|---|--------|---------------------|
| 1 | 레시피에 `사용자 입력 변수`가 **1개 이상** 정의됨 + 발화/기본값으로 다 채워지지 **않음** | ✅ 실행 시작 직전 1회 (미충족 필드만) |
| 2 | **값 확인 후 실행** 모드 | ✅ 실행 시작 직전 1회 (모든 입력 변수, 기본값은 프리필) |
| 3 | 바로 실행 모드 + 모든 필수 변수가 발화/기본값으로 충족됨 | ❌ 안 뜸 (바로 실행) |
| 4 | 사용자 입력 변수가 **정의되지 않은** 레시피 | ❌ 안 뜸 |

- **"API 스텝이 참조하는 `{{userInput.X}}`가 비어 있으면 자동으로 액션 피커를 띄우는가?"**
  → **아니오(프로토타입).** 액션 피커는 레시피 메타의 `사용자 입력 변수` 정의를 기준으로만 렌더링한다.
    API 스텝의 body/path에 쓰인 `{{userInput.X}}`를 역파싱해 즉석에서 필드를 만들지 않는다.
  → 레시피 작성 시 API 스텝이 참조하는 `userInput` 키는 **반드시 메타의 `사용자 입력 변수`에도 선언**되어야 한다(작성 규칙). 선언이 누락돼 실행 시 값이 비면 아래 "값 누락 처리"를 따른다.

### 바로 실행 모드에서 값 부족 처리 (확정)

바로 실행(MODE=AUTO) 모드에서 필수 `userInput` 값이 발화·기본값·AI 추출로도 채워지지 않은 경우:

| 상황 | 처리 |
|------|------|
| 미충족 변수가 **메타에 선언되어 있음** | 실행 시작 직전 **액션 피커로 미충족 필드만** 물어봄 (`input_waiting`). 바로 실행이라도 이 경우만 예외적으로 노출 |
| 미충족 변수가 **메타에 선언되지 않음**(작성 누락) | 실행 **실패 처리**. 해당 스텝 ❌ + "필수 입력값(X)이 없습니다" 메시지. 액션 피커를 즉석 생성하지 않음 |

- 즉 "실행 실패 vs 액션 피커"의 갈림은 **변수가 레시피 메타에 선언되었는지** 여부다. 선언된 값만 액션 피커로 물을 수 있다.
- AUTO 모드에서 액션 피커가 뜨는 것은 값 미충족 예외 상황 한정이며, 값이 다 있으면 [바로 실행]은 중단 없이 진행된다.

### 액션 피커 응답 후 실행 재개 흐름 (확정)

```
레시피 매칭 → 모드 선택
    │
    ▼
입력 변수 충족 검사
    ├─ 다 채워짐 → 바로 실행(executing)
    └─ 미충족 → 액션 피커 노출 (session_status: input_waiting)
                    │
                    ▼
        사용자 입력 완료 → POST /api/v1/action-picker/respond
                    │  { executionId, stepIndex, values }
                    ▼
        서버: values를 실행 context(userInput.*)에 병합
              → input_waiting 해제 → executing 전파(SSE)
                    │
                    ▼
        레시피 첫 스텝부터 순차 실행 → PROGRESS 메시지 갱신(message_update)
                    │
                    ▼
        완료 → PROGRESS 확정(message_update) + RESULT(message_new) → session_status: idle
```

- 프로토타입은 pre-run 수집이므로 respond의 `stepIndex`는 **입력을 수집한 사용자 입력 스텝의 인덱스**를 가리킨다.
  실행 전 메타 변수 일괄 수집(USER_INPUT 스텝 없음)인 경우 `stepIndex`는 `-1`(pre-run 마커)로 보낸다.
- respond는 서버가 상태를 `input_waiting → executing`으로 바꾸고 SSE로 전파한 뒤 실행을 재개한다. FE가 단독으로 상태를 바꾸지 않는다. (상태 해제 원칙: [messaging.md](../common/messaging.md#상태-해제-취소--중지--완료))
- respond 실패(검증 에러 등) 시 서버는 `input_waiting`을 유지하고 액션 피커를 다시 노출한다.

## 실행 중 진행 상태 표시

진행 상태 블록은 대화 메시지처럼 스크롤되는 형태로 표시 (상단 고정 아님).

```
📋 입사지원 실행 중

✅ 1. 로그인 확인
✅ 2. 이력서 확인 — "프론트엔드 개발자 이력서" 발견
⏭️ 3. 회원가입 (스킵)
🔄 4. 공고 선택 (입력 대기 중)
⬜ 5. 입사지원 제출
⬜ 6. 결과 확인
```

| 아이콘 | 의미 |
|--------|------|
| ✅ | 완료 — 옆에 결과 한 줄 표시 (30자 이내) |
| 🔄 | 실행 중 / 입력 대기 |
| ⬜ | 대기 |
| ⏭️ | 조건 미충족으로 스킵 |
| ❌ | 실패 |

- 사용자 입력 필요 시 해당 스텝에서 액션 피커 노출
- 레시피 연속 실행 시 이전 실행 결과도 스크롤로 확인 가능

## 실행 중 입력 제한

한 대화방에서 동시에 여러 요청을 보낼 수 없음 (대화방 단위 락).
상태는 `session_status`(SSE)로 전달되며, **여러 탭에서 같은 대화방을 열어도 모든 탭의 입력 영역이 동기화**된다. 상태값/이벤트 정의는 [messaging.md](../common/messaging.md#대화방-처리-상태-session_statusstatus) 참조.

| status | 입력 영역 |
|--------|-----------|
| `ai_responding` (AI 응답 생성 중) | 입력 잠금 + "⏳ 답변이 진행 중입니다" 표시 |
| `executing` (레시피/플랜 실행 중) | 입력 잠금 + "⏳ 레시피 실행 중... [중지]" 표시 |
| `input_waiting` (사용자 입력 대기) | 액션 피커만 활성화, 자유 채팅 잠금 |
| `idle` (유휴) | 정상 사용 |

- 입력이 잠긴 이유를 **입력 영역에 명시**하여, 다른 탭에서도 "왜 채팅이 안 되는지" 즉시 인지 가능
- 다른 대화방으로 이동하면 해당 대화방은 독립적으로 사용 가능

### 중지 버튼

```
┌─────────────────────────────────────────────┐
│  레시피 실행 중...                    [중지]  │
└─────────────────────────────────────────────┘
```

- [중지] 클릭 → **중지 API 호출** (`POST /api/v1/conversations/{id}/stop`) → 현재 스텝까지 결과 저장, 이후 스텝 취소
- 서버가 `session_status: idle`로 해제 + SSE 전파 → 모든 탭 입력 잠금 해제
- 진행 상태 블록에 중단 표시

### 취소 동작

- 액션 피커에서 [취소] 클릭 → **취소 API 호출** (`POST /api/v1/conversations/{id}/cancel`) → 전체 레시피 중단
- 서버가 대기/락 해제 후 `session_status: idle` 전파 + AI "취소되었습니다" 메시지(message_new)
- **FE 단독으로 액션 피커만 닫으면 안 됨** — 서버 상태가 `input_waiting`으로 남아 다른 탭·새로고침 시 다시 잠김
- 취소/중지는 **멱등** (이미 idle이면 no-op). 상세: [messaging.md 상태 해제](../common/messaging.md#상태-해제-취소--중지--완료)

## 실행 완료 / 결과 요약

모든 스텝이 종료(성공/스킵)되면 서버가 **결과 메시지**(`message_new`)를 발행하여 사용자에게 실행 결과를 알린다. 결과 메시지 생성 방식은 레시피에 **결과 메시지 템플릿(⑤)** 이 있는지에 따라 갈린다.

```
스텝 전부 종료
    │
    ├─ ⑤ 템플릿 있음 → BE가 실행 context로 {{변수}} 치환 (AI 미호출)
    │
    └─ ⑤ 템플릿 없음 → [fast] AI 요약 (입력: steps summary + resultValues)
    │
    ▼
PROGRESS 확정(message_update) + RESULT 메시지(message_new) 발행 + 결과 제공형 카드
    │
    ▼
session_status: idle + 히스토리 refresh
```

### (a) 템플릿이 있는 경우 — BE 치환 (AI 미호출)

- BE가 ⑤ 템플릿의 `{{변수}}`를 실행 context 값으로 치환해 결과 메시지(`message_new`)를 발행한다.
- 치환에 쓰는 변수 범위는 **④ 결과 정의 변수 + ② 사용자 입력 변수**로 한정한다. (규칙: [authoring.md ⑤ 결과 메시지 템플릿](authoring.md#⑤-결과-메시지-템플릿))
  - 스텝의 extract 원시 변수를 템플릿에서 직접 참조하지 않는다. 템플릿에서 쓰려는 값은 반드시 ④ 결과 정의에 등록해 경유한다.
- AI를 호출하지 않으므로 원시 응답을 AI에 넘기는 일이 없다.

### (b) 템플릿이 없는 경우 — fast AI 요약

- `[fast]` 모델로 결과를 요약한다. AI 입력은 **스텝별 summary(steps)** 와 **resultValues**(④ 결과 정의로 추린 값)만 전달한다.
- **원시 응답(raw response) 전체를 AI에 넘기지 않는다.** 스텝 summary와 결과 정의 값만 전달하여 토큰/민감정보 노출을 최소화한다.
- 상세 입력/출력/프롬프트: [시나리오: 결과 요약](../chat/scenarios/result-summary.md)

### 결과 표시 (프로토타입 스코프)

| 요소 | 프로토타입 | 후속 |
|------|-----------|------|
| 결과 메시지(텍스트) | ✅ 채팅에 표시 (Markdown) | — |
| 결과 제공형 카드 (레시피명 + 실행 시각) | ✅ 표시 | — |
| 카드의 [결과 보기] | ⛔ 비활성/생략 (사이드 패널 미구현) | 사이드 패널 결과 상세 연결 |
| 히스토리 목록 refresh | ✅ | — |

- 사이드 패널이 프로토타입에서 미구현이므로, **결과 메시지(텍스트) 표시가 결과 전달의 주 경로**다.
- 결과 제공형 카드는 노출하되 `[결과 보기]`는 후속으로 미룬다(비활성 또는 생략). 카드 유형 정의는 [card-ui.md](../chat/card-ui.md#유형) 참조.

## 플랜 실행

여러 레시피를 조합한 실행 계획(플랜)의 경우, 각 레시피가 순차 자동 실행됨.
상세: [플랜](plan.md)

## 예외 시나리오

### 스텝별 상태 저장

각 스텝 실행 완료 시 서버에 API 호출하여 상태를 저장. 이를 통해 새로고침/중단 후 복원, 히스토리 상세 조회가 가능.

#### 저장 대상

| 저장 | 안 저장 |
|------|---------|
| **실행 시점 레시피 스냅샷** (원본 독립) | — |
| extract된 변수 (context) | — |
| 스텝 상태 (성공/실패/스킵) | — |
| 에러 메시지 | — |
| 사용자 입력값 | — |
| 원시 응답 전체 (선택적, 1MB 초과 시 잘라서 저장) | — |

#### 레시피 스냅샷 (히스토리 재현)

- 실행 시작 시점의 레시피(메타+스텝+변수+결과정의)를 **통째로 복사 저장**한다.
- 이후 원본 레시피가 수정/삭제되어도, 히스토리에서 "그때 그 실행"을 정확히 재현할 수 있다.
- 원본 레시피 링크(ID)는 참고용으로 유지하되, 표시는 스냅샷 기준.
- 상세 스키마: [db/execution.md](../../db/execution.md) `EXECUTION_RECIPE.RECIPE_SNAPSHOT_JSON`

#### 복원 방식

"이어서 실행" 시 서버에서 저장된 context를 내려주고, 프론트가 다음 스텝부터 이어서 실행.

#### 민감 데이터 (추후 고려)

스텝 결과에 토큰, 비밀번호, 개인정보 포함 가능. 추후 저장 시 민감 필드 마스킹 정책 필요.

### 브라우저 새로고침 / 탭 닫기

API 호출은 사용자 브라우저에서 실행되므로, 브라우저가 닫히면 실행도 중단됨.

| 동작 | 처리 |
|------|------|
| 새로고침 | 대화방 재진입 시 실행+스텝을 서버에서 조회해 진행 블록 복원(아래). 브라우저 종료로 중단된 RUNNING 실행은 "중단됨"으로 표시. [이어서 실행] 버튼 제공 |
| 탭 닫기 후 재방문 | 동일 |

**진행 블록 복원 (메시지-실행 연결)**

- 진행 블록은 FE 메모리(zustand)가 아니라 **PROGRESS 메시지로 저장**되므로, 대화 메시지를 로드하면 그대로 복원된다. 결과도 RESULT 메시지로 저장된다. (계약: [messaging.md 저장/전달 내부 계약](../common/messaging.md#저장전달-내부-계약-febe-공유))
- 실행-촉발 위치 연결은 `EXECUTION.MESSAGE_ID`(실행의 PROGRESS 메시지)로 한다. 대화 진입 시 메시지 로드로 PROGRESS/RESULT가 복원되고, 이후 갱신은 SSE(`message_update`로 PROGRESS 갱신, 완료 시 RESULT `message_new`).
- 스키마/인덱스: [db/execution.md `EXECUTION.MESSAGE_ID`](../../db/execution.md#새로고침-복원-메시지-실행-연결)

**이어서 실행**

- "이어서 실행" = 마지막 성공한 스텝 다음부터 재개
- **필수 전제**: 스텝 실행 결과(context)를 서버에 중간 저장해야 이어서 실행 가능
- 프로토타입에서는 "처음부터 다시 실행"만 제공하고, 이어서 실행은 추후 구현 가능

### 네트워크 끊김

| 단계 | 처리 |
|------|------|
| 감지 | API 호출 타임아웃 또는 fetch 에러 발생 |
| 표시 | 해당 스텝 ❌ + "네트워크 연결을 확인해주세요" 메시지 |
| 재시도 | [다시 실행] 버튼 (해당 스텝부터 재개) |
| 자동 재시도 | 하지 않음 (사용자가 확인 후 수동 재시도) |

### 외부 서버 접속 불가

네트워크는 정상이나 대상 서버가 내려간 경우 (connection refused):
- 해당 스텝 ❌ + "대상 서버(XX)에 접속할 수 없습니다" 메시지
- 사용자가 "내 문제인지, 서버 문제인지" 구분 가능

### 서브레시피 실패 시 부모 레시피 동작

서브레시피 내부에서 실패 시:
- 기본 동작: 부모의 해당 스텝도 실패 처리 (❌) → 부모 레시피 전체 중단
- 에러 메시지에 "어느 서브레시피의 어느 스텝에서 실패했는지" 표시

```
❌ 3. 회원가입 — "이메일 인증 발송" 스텝에서 실패 (500)
```

**onError 옵션** (서브레시피 호출 스텝에 설정 가능):

| 값 | 동작 |
|------|------|
| `stop` (기본값) | 서브레시피 실패 → 부모 레시피 중단 |
| `skip` | 서브레시피 실패 → 해당 스텝 스킵하고 다음 스텝으로 진행 |

### 레시피 실행 중 대화방 삭제

- 실행 중인 대화방은 삭제 차단
- "레시피 실행 중입니다. 중지하고 삭제하시겠습니까?" 확인 팝업
- 확인 시: 레시피 중단 → 대화방 삭제 (히스토리는 유지)

### 타임아웃

| 항목 | 값 |
|------|---|
| 스텝 단위 타임아웃 | 30초 (설정 가능) |
| 레시피 전체 타임아웃 | 5분 (설정 가능) |

타임아웃 발생 시:
- 해당 스텝 ❌ + "응답 시간 초과" 메시지
- [다시 실행] 버튼 표시

### 액션 피커 입력 대기 중 무응답

- 타임아웃 없음 (무기한 대기)
- 사용자가 [취소]로 중단하거나, 다른 대화방에서 다른 작업 가능
- 대화방 상태 🟡 (입력 대기)로 유지
- 나중에 돌아와서 입력 이어가기 가능

## 대화 내 연속 실행

하나의 대화에서 여러 레시피를 연속 실행 가능.
