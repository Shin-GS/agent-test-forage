# 플랜 (Plan)

## 개요

AI가 사용자 발화를 분석하여 기존 레시피 여러 개를 조합한 1회성 실행 계획. 저장하지 않음.

- **레시피** = 등록된 작업 (저장, 재사용)
- **플랜** = AI가 레시피 여러 개를 조합한 실행 계획 (1회성)
- 플랜 판단 기준 = 레시피 개수가 아니라 **"결과가 앞→뒤로 흐르는 순차 실행 필요 여부"**. 판단 규칙: [intent-classification.md 4-way 판단 규칙](../chat/scenarios/intent-classification.md#4-way-판단-규칙-실행-의도).

> 이 문서는 **플랜 1단계** 스코프와 **2단계 일부(제안 카드 스킵 + 순서변경 + 값 사전 편집, [이어서 실행](PARTIAL 재개))**를 확정 기술한다. 제안 카드의 스킵·순서변경·값 사전 편집은 [제안 카드 편집](#제안-카드-편집-2단계--스킵--순서변경--값-사전-편집)에서, 실패/중단 지점부터의 재개는 [이어서 실행 (PARTIAL 재개)](#이어서-실행-partial-재개)에서 확정한다. 레시피 추가/제거·복잡한 데이터 매핑은 [2단계 백로그](#2단계-백로그)로 남긴다.

## 내부 구현 통일: 단일 = N=1 플랜

**모든 실행은 내부적으로 하나의 EXECUTION으로 처리**한다(단일 레시피 = 레시피 1개짜리 플랜). 경로를 통일해 오케스트레이션 코드를 단일화한다.

- EXECUTION은 실행 사실의 진실 계층이다([messaging.md EXECUTION 계층](../common/messaging.md#execution-계층사실히스토리)).
- 실행 대상 레시피들은 순서대로 `EXECUTION_RECIPE`로 이어 붙는다(단일이면 1개).
- 사용자에게 **보여줄 때만** 단일/플랜을 구분한다.

| 조건 | 표시 |
|------|------|
| 레시피 1개 (N=1) | "레시피 실행" 형태 (플랜이라는 말 안 씀) |
| 레시피 2개 이상 | "플랜" 형태 (묶음 표시) |

## 플로우

```
사용자 발화: "입사지원 해줘"
    │
    ▼
AI 분석: propose_plan(recipeIds, rationale) — 결과 의존 순차 조합 판단
    │
    ▼
플랜 제안 카드 (액션 피커, 읽기 전용 미리보기 + rationale 근거)
    │
    ├─ 사용자 [취소] → 취소 API → "취소되었습니다" (아무 실행 안 함)
    │
    └─ 사용자 [자동 실행] 클릭
         │
         ▼
    플랜 실행 (레시피 순차 자동 실행 — BE 오케스트레이션)
         │
         ├─ 각 레시피 완료 시: 결과 저장 + 다음 레시피로 CONTEXT 전달
         ├─ 다음 레시피 pre-run 입력 필요 시: 액션 피커 (해당 레시피 기준)
         ├─ 실패 시: 전체 중단 → PARTIAL 확정 후 종료 → [플랜 중단] / [이어서 실행](실패 지점부터 재개)
         │
         └─ 전체 완료: PROGRESS 확정 + RESULT + 결과 카드 + idle
```

플랜 제안 카드 상세: [plan-proposal.md](../chat/scenarios/plan-proposal.md).

## 제안 카드 편집 (2단계 — 스킵 + 순서변경 + 값 사전 편집)

플랜 제안 카드는 실행 전에 **인터랙티브**하다. 사용자는 세 가지를 조정할 수 있다.

1. **레시피 스킵** — 각 행 체크박스로 특정 레시피를 실행 대상에서 제외.
2. **순서변경** — ↑/↓ 이동 버튼으로 실행 순서를 재배치(드래그 아님, 키보드 조작 가능).
3. **값 사전 편집** — 각 레시피 행의 [값 지정] 아코디언에서 입력 변수를 실행 전에 미리 편집. 목적은 **자동 실행이 중간에 pre-run 액션 피커로 멈추지 않고 쭉 흐르게** 하는 것.

### 스킵 · 순서변경 — 전부 FE에서 해결 (BE 계약 불변)

스킵·순서변경 편집은 **BE 계약을 바꾸지 않는다.** BE는 이미 `startPlan`(POST `/conversations/{id}/plan-executions {recipeIds}`)에 전달된 `recipeIds` 배열을 **받은 순서대로** 실행하고, 배열이 1개면 내부적으로 SINGLE(N=1 플랜)로 수렴한다([내부 구현 통일](#내부-구현-통일-단일--n1-플랜)).

| 편집 동작 | FE 처리 | BE 관점 |
|-----------|---------|---------|
| 스킵 | 체크 해제된 레시피를 `recipeIds` 배열에서 제외 | 애초에 안 넘어온 것과 동일 |
| 순서변경 | 화면에 보이는 순서대로 `recipeIds` 배열 재정렬 | 넘어온 배열 순서대로 실행 |

- FE는 **체크된 항목만, 화면 순서대로** 배열을 만들어 `startPlan`에 전달한다.
- 조정 결과가 1개면 BE가 SINGLE로 수렴하므로 별도 분기 불필요.

### 값 사전 편집 — 카드 payload 자족 + startPlan 확장

값 사전 편집은 스킵·순서변경과 달리 **BE 계약을 확장**한다(요청 바디에 `recipeInputs` 추가, 실행 시 레시피별 시드). 별도 API 조회 없이 **제안 카드 payload만으로** 편집 UI를 그린다.

> **payload 크기 트레이드오프(인지함)**: 각 레시피의 `variables`(변수 정의)를 카드 payload에 싣는다. 레시피당 변수는 통상 소수(수 개)라 실무상 문제되지 않으며, 별도 스키마 조회 라운드트립을 없애 UX·단순성을 얻는 의도적 선택이다. select 옵션이 매우 큰 변수 등 예외적으로 payload가 커지는 경우가 관찰되면 그때 지연 조회로 전환한다(현재는 미도입).

#### 결정 1. 값의 키 = sequence (배열 순서, 0-based)

- `startPlan` 요청은 `recipeInputs: List<Map<String, Object>>`로 확장한다. **배열 인덱스 = `recipeIds` 인덱스 = 실행 순서**로 정렬한다.
- `recipeId`를 키로 쓰지 않는다 — 같은 레시피가 플랜에 **중복**될 수 있어 충돌하기 때문이다.
- 스킵·순서변경으로 최종 `recipeIds` 배열이 정해진 뒤, **그 순서에 맞춰 `recipeInputs`도 정렬**해 전달한다(같은 sequence로 짝지음). 스킵된 레시피의 입력값은 배열에서 함께 제외한다.
- 특정 레시피를 편집하지 않았으면 그 자리(sequence)는 빈 맵 `{}`으로 채워 배열 길이를 `recipeIds`와 일치시킨다.

```
recipeIds     = [3, 5, 1]      // 스킵/순서변경 반영된 최종 실행 순서
recipeInputs  = [               // 같은 인덱스 = 같은 레시피
  { "직무": "백엔드", "지역": "서울" },   // sequence 0 → recipeId 3
  {},                                     // sequence 1 → recipeId 5 (미편집)
  { "지원 메모": "경력직 지원" }           // sequence 2 → recipeId 1
]
```

#### 결정 3. 변수 스키마를 카드 payload에 전달

현재 제안 카드는 `inputPreview`(기본값만) 뿐이라 편집 UI(타입/옵션/필수)를 그릴 수 없다. 각 레시피 payload에 **`variables`(전체 변수 정의)**를 추가로 실어 FE가 기존 액션 피커 필드 컴포넌트를 재사용해 편집 폼을 그린다. 별도 API 조회 없이 카드 payload로 자족한다.

| 필드 | 설명 |
|------|------|
| `name` | 변수 key (= `recipeInputs` 맵의 키, 시드 대상) |
| `label` | 표시명 ([표시명 폴백 체인](../../glossary.md) 적용) |
| `type` | 입력 타입 (text / number / select / boolean 등 — 액션 피커 필드 타입과 동일) |
| `required` | 필수 여부 (편집 폼 검증 + pre-run 통과 판정에 사용) |
| `default` | 기본값 (있으면 편집 폼 초기값) |
| `options` | select류 선택지 |

- `variables`는 액션 피커 pre-run 필드 정의와 **같은 스키마**를 재사용한다([execution.md 사용자 입력 수집](execution.md#사용자-입력-수집-액션-피커)).

#### 우선순위 상 위치

사전 편집값은 그 레시피의 `userInput`으로 시드되어 **최우선으로 실행에 투입**된다(사전 편집 > 발화 > 기본값). 이전 결과(🔗)는 사용자가 그 key를 명시하지 않았을 때 자동 채움으로 쓰인다. 상세는 [데이터 자동 채움 우선순위](#데이터-자동-채움-우선순위-실행-중-액션-피커) 표 참조.

### 조정 상태는 저장하지 않음

- 사용자의 스킵/순서변경/**값 사전 편집**은 **카드 로컬 상태로만** 관리한다. 서버에 저장하지 않는다.
- 카드 payload(원본 `recipeIds`/`recipes`)는 그대로 둔다. **새로고침 시 AI가 제안한 원래 배열로 복원**된다(편집값도 사라짐).
- **편집값은 행 단위로 보존한다**: 어떤 레시피를 편집한 뒤 스킵했다가 다시 체크해도 그 행의 편집값은 유지된다(스킵은 실행 포함 여부만 토글, 편집 내용을 지우지 않는다). 순서변경으로 행이 이동해도 편집값은 그 행을 따라간다.
- 최종 조정 결과는 [자동 실행] 시점에 `startPlan` 요청 바디(`recipeIds` + `recipeInputs`)로만 반영된다.

### UX 규칙 (확정)

각 행 구성:

```
[↕ ↑/↓] [☑] [순서번호] 레시피명  [서비스 뱃지]  [값 지정 ▸] (값 지정됨)
                       값 미리보기 (기존 유지)
         └ (펼침) 변수 입력 폼 — 그 레시피의 입력 변수 전부
```

- **순서번호는 체크된 항목만** 세어 1, 2, 3… 재매김한다. 스킵된 행은 흐리게 처리 + "(제외됨)" 표기, 순서번호를 부여하지 않는다.
- **헤더 카운터**: "(전체 N단계 중 M단계 실행)". 스킵을 반영해 실시간 갱신한다.
- **최소 1개 선택 가드**: 전부 스킵이면 [자동 실행]을 비활성화하고 "최소 1개 선택" 안내를 노출한다.
- **1개만 남으면** 그대로 실행한다(BE가 SINGLE 수렴). 버튼 문구는 "자동 실행"을 유지한다.
- **실행/취소 후 편집 잠금**: [자동 실행] 또는 [취소] 이후에는 카드 편집이 잠긴다.

#### 값 지정 아코디언 (결정 4)

- 각 레시피 행에 **[값 지정] 토글**을 둔다. **기본은 접힘** — 접혀 있으면 카드는 기존처럼 깔끔하다.
- 펼치면 그 레시피의 **변수 입력 폼**을 노출한다. 폼은 카드 payload의 `variables`(변수 스키마)로 그리며, 기존 **액션 피커 필드 컴포넌트를 재사용**한다.
- **노출 범위 = 그 레시피의 입력 변수 전부.** 기본값이 있는 변수도 편집할 수 있다.
- 값을 편집한 레시피는 행에 **"값 지정됨" 뱃지**를 표기한다(어느 레시피를 손봤는지 한눈에).
- **스킵된 레시피는 아코디언을 비활성화**한다(실행 대상이 아니므로 편집 무의미).
- 편집값은 스킵/순서변경과 동일하게 **카드 로컬 상태**로만 관리한다. 서버에 저장하지 않으며, 새로고침 시 AI 제안 원본으로 복원된다.
- 접근성: 아코디언 토글은 `aria-expanded`로 상태를 노출하고, 펼침/접힘을 키보드로 조작할 수 있다.

### 접근성

- 순서변경은 ↑/↓ 이동 버튼으로 제공한다(드래그 미사용, 키보드 조작 가능).
- 이동 시 **aria-live로 announce**한다(예: "포지션 탐색을 2번째로 이동했습니다").

## 실행 계약 (BE 오케스트레이션) — 중대

플랜 실행의 전이·완료는 **BE가 자동 판단**한다. FE는 스텝 결과만 보고한다.

### FE 역할: reportStep만 호출

- **FE는 각 스텝 실행 결과를 `reportStep`으로 보고만 한다.** (API 호출은 브라우저에서 실행되므로)
  - **성공/실패/스킵을 모두 보고한다.** SKIP도 종료 상태로 보고되며(조건 미충족 등), BE는 이를 PENDING이 아닌 종료 상태로 취급한다.
- **FE는 실행 완료(complete)를 호출하지 않는다.** ← 기존 계약 변경. 실행 전이·완료 판단은 전적으로 BE가 한다.

### BE 역할: reportStep 수신 시 오케스트레이션

BE는 `reportStep`을 받을 때마다 현재 위치를 기준으로 다음을 자동 판단한다. **"현재 레시피의 마지막 스텝인가"는 남은 PENDING 스텝 유무로 판단한다**(스텝 순번이 아니라 잔여 PENDING 기준 — SKIP/실패도 종료 상태로 소진됨).

```
reportStep 수신
    │
    ├─ 보고가 실패(FAILED)임
    │     → 전체 중단. EXECUTION=PARTIAL 확정. 다음 레시피 전이 판단하지 않음.
    │     → 실패 레시피는 FAILED 확정, 미실행 레시피는 PENDING으로 **보존**(FAILED로 덮지 않음 — 재개 시작 지점 판별용, 실패 처리·[이어서 실행] 참조)
    │     → PROGRESS 실패 확정(message_update) + [플랜 중단] / [이어서 실행] 안내 (실패 처리 참조)
    │
    └─ 보고가 성공/스킵임
          │
          ├─ 현재 레시피에 남은 PENDING 스텝이 있음 (= 마지막 아님)
          │     → PROGRESS 갱신 (message_update). 다음 스텝 대기.
          │
          └─ 현재 레시피에 남은 PENDING 스텝이 없음 (= 그 레시피 완료)
                │
                ├─ 다음 EXECUTION_RECIPE 있음
                │     → 다음 레시피 RUNNING 전이
                │     → 스텝 생성
                │     → 해당 sequence의 recipeInputs 시드 (사전 편집값)
                │     → CONTEXT 매핑 (같은 key 자동 전달)
                │        ├─ required 다 채워짐 → pre-run 액션 피커 없이 통과 (자동 실행 안 멈춤)
                │        ├─ 매핑되면 → 바로 실행 진행
                │        └─ 미충족 필수값 있으면 → 해당 레시피 pre-run 액션 피커 (input_waiting)
                │
                └─ 다음 EXECUTION_RECIPE 없음 (마지막 레시피까지 종료)
                      → 실행 자동 완료 (outcome=SUCCESS)
                      → PROGRESS 확정 + RESULT 발행 + session_status: idle
```

- 스텝 성공/실패/스킵 판정, 다음 레시피로의 전이, 최종 완료는 모두 BE 판단이다. FE가 상태를 임의로 바꾸지 않는다(상태 해제 원칙: [messaging.md 상태 해제](../common/messaging.md#상태-해제-취소--중지--완료)).
- 이벤트 흐름은 단일 레시피와 동일하게 CHAT 메시지로 흐른다: PROGRESS `message_update`, 완료 시 RESULT `message_new`([messaging.md 실행 SSE 흐름](../common/messaging.md#실행-sse-흐름-message_new--message_update)).

### 사전 편집값 시드 (레시피별 recipeInputs)

- **각 레시피가 RUNNING으로 전이될 때**, 그 레시피의 sequence에 해당하는 `recipeInputs` 맵을 시드한다. 기존에는 `initialContext`가 **첫 레시피에만** 시드되었으나, 이를 **레시피별로 확장**한다.
- 시드된 사전 편집값으로 그 레시피의 **required가 모두 채워지면** pre-run 액션 피커 없이 통과한다 → 자동 실행이 중간에 멈추지 않는다.
- **병합 규칙(같은 key 충돌 시)**: BE 시드 시점에 `userInput = 기본값 → 발화값(initialContext) → 사전 편집값(recipeInputs)` 순으로 덮어써 만든다(뒤가 이김 → 사전 편집 > 발화 > 기본값). 사용자가 명시한 값(사전 편집/발화)이 그 레시피 실행에 그대로 투입된다. 이전 결과(🔗)는 CONTEXT 최상위에 별도 누적되며, 사용자가 그 key를 명시하지 않았을 때 자동 채움으로 쓰인다([데이터 자동 채움 우선순위](#데이터-자동-채움-우선순위-실행-중-액션-피커) 참조).
- required가 여전히 미충족이면(사전 편집을 안 했거나 일부만 채움) 기존처럼 해당 레시피 pre-run 액션 피커로 물어본다.
- FE는 [자동 실행] 시 체크된 항목만 화면 순서대로 `recipeIds`를 만들고, 같은 순서로 `recipeInputs`를 정렬해 `startPlan`에 전달한다([값 사전 편집](#값-사전-편집--카드-payload-자족--startplan-확장)).

### 레시피 간 데이터 매핑 (1단계 단순 규칙)

레시피 A의 결과를 레시피 B가 쓰는 경우, 1단계는 **단순 규칙**만 지원한다.

| 상황 | 처리 |
|------|------|
| B의 입력 key가 이전 결과(CONTEXT)에 **같은 이름**으로 있음 | 자동 전달 (🔗 이전 결과) |
| 같은 key가 없음 | B의 pre-run 액션 피커로 사용자에게 물어봄 (✏️ 직접 입력) |

- 서로 다른 key 간 매핑(예: `resumeId` → `attachmentId`)은 [2단계 백로그](#2단계-백로그).

### 액션 피커 일반화 (레시피별 pre-run)

액션 피커는 "**현재 RUNNING인 `EXECUTION_RECIPE`의 pre-run 입력 수집**"으로 일반화된다.

- 각 레시피가 RUNNING으로 전이될 때, 그 레시피의 미충족 입력 변수만 액션 피커로 수집한다.
- `action_picker_response`(respond)는 **현재 레시피 기준**으로 값을 병합하고 실행을 재개한다.
- 단일 레시피 실행도 같은 메커니즘(N=1 플랜의 첫 레시피 pre-run)이다. 상세: [execution.md 사용자 입력 수집](execution.md#사용자-입력-수집-액션-피커).

## 데이터 자동 채움 우선순위 (실행 중 액션 피커)

실행 중 각 레시피 pre-run 시점의 값 채움 우선순위. (제안 시점 미리보기와 다름 — 아래 참고)

사용자 명시 입력(사전 편집·발화)은 실행 시작/전이 시점에 그 레시피의 `userInput`으로 **시드**되고, 이전 레시피 결과(🔗)는 실행 중 스텝 결과가 CONTEXT 최상위에 **누적**된다. 아래 우선순위는 "레시피에 실제 투입되는 값" 기준이다.

| 우선순위 | 소스 | 뱃지 | 저장 위치 |
|---------|------|------|-----------|
| 1 | 제안 카드에서 사용자가 실행 전 명시한 값 (recipeInputs) | ✍️ 사전 편집 | userInput (시드) |
| 2 | 사용자 발화에서 AI가 추출 | 🗣️ 발화 | userInput (시드, 첫 레시피) |
| 3 | 레시피에 정의된 기본값 | 📌 기본값 | userInput (시드) |
| 4 | 이전 레시피 실행 결과 (CONTEXT, 같은 key) | 🔗 이전 결과 | CONTEXT 최상위 (누적) |
| 5 | 채울 수 없음 → 액션 피커로 물어봄 | ✏️ 직접 입력 | userInput (병합) |

- **사용자가 명시한 값(사전 편집 ✍️ / 발화 🗣️)이 최우선이다.** 이들은 그 레시피의 `userInput`으로 시드되며, 실행 투입(required 충족 판정·템플릿 `userInput.*` 치환)은 `userInput`을 본다. 같은 key면 사전 편집이 발화값을 덮는다(둘 다 userInput 레이어, 뒤가 이김).
- **이전 결과(🔗)는 사용자 명시값이 없을 때만 자동 채움으로 기능한다.** 레시피 간 데이터가 같은 key로 흐르는 경우(사용자가 그 key를 편집하지 않았으면) 이전 결과가 활용된다. 사용자가 그 key를 사전 편집/발화로 명시했다면 **사용자 값이 우선**한다 — "사용자가 방금 지정한 값"을 시스템이 임의로 덮지 않는다는 원칙(사용자 의도 존중).
  - 실행 투입 경로(required 충족 판정·템플릿 `userInput.*`)는 `userInput`을 기준으로 하므로, 사용자 명시값이 있으면 그 값이 그대로 쓰인다. 이전 결과는 결과 조회/표시(resultValues) 산출 시 CONTEXT 최상위에서 우선 참조된다.
- **제안 시점(플랜 제안 카드)에는 🔗 이전 결과를 예측 표시하지 않는다.** 실행 전엔 확정 불가하므로 "실행 중 결정"으로만 표시한다([plan-proposal.md 값 미리보기](../chat/scenarios/plan-proposal.md#값-미리보기-결정-1--정직하게-축소)).
- 사전 편집값은 제안 카드 [값 지정] 아코디언에서 입력한다([값 사전 편집](#값-사전-편집--카드-payload-자족--startplan-확장)). 실행 중 액션 피커에서의 값 편집도 그대로 가능하다(해당 레시피 pre-run).

## 실행 중 진행 상태

진행 카드는 레시피 그룹 단위로 표시하고, **현재 실행 중인 레시피만 스텝을 펼친다**(완료된 레시피는 접힘 + 결과 한 줄).

```
📋 플랜 실행 중  (2/3 레시피)

✅ 1. 이력서 작성 — 이력서 ID: RES-001
🔄 2. 포지션 탐색
   ├ ✅ 로그인
   ├ 🔄 포지션 목록 조회
   └ ⬜ 결과 추출
⬜ 3. 입사지원
```

- 헤더에 진행률 `(k/N 레시피)` 표시.
- 완료된 레시피는 접힘(결과 한 줄만), 현재 레시피만 스텝 펼침.
- 레시피 전이 시 **aria-live로 announce**(접근성): 예 "포지션 탐색 실행을 시작합니다".
- 진행 블록은 PROGRESS 메시지로 저장되어 새로고침 시 복원된다([messaging.md PROGRESS](../common/messaging.md#progress-실행-진행-블록)).

## 실행 모드

플랜 시작 시 [자동 실행] 한 번 승인 → 쭉 자동 진행. 중간에 사용자 입력이 필요할 때만 해당 레시피 pre-run 액션 피커로 멈춘다.

(레시피 단위 승인 없음 — 플랜의 목적이 "묶어서 한번에"이므로. 플랜 모드는 항상 AUTO.)

## 실패 처리

- 실패 시: **전체 중단 후 `PARTIAL`로 확정하고 종료**한다.
- 안내: "레시피 N에서 실패했습니다. 레시피 1~(N-1)은 이미 완료되었습니다."
- **미실행(PENDING) 레시피는 PENDING으로 보존**한다(FAILED로 덮지 않음). 그래야 재개 시 "완료(SUCCESS)/실패(FAILED)/미실행(PENDING)"을 구분해 재개 시작 지점을 찾을 수 있다. PARTIAL 종료된 실행 하위에 PENDING 레시피가 남는 것은 "재개 가능한 부분 완료"의 정확한 표현이다.
- 이미 실행된 레시피의 결과는 되돌릴 수 없음 (외부 서버에 데이터 생성됨).
- **확인 없이 자동 재시도하지 않는다.** 재개는 사용자가 [이어서 실행]을 눌러야 시작된다.

### 실패 후 선택지 (카드 버튼)

| 버튼 | 동작 |
|------|------|
| [이어서 실행] | 실패 지점부터 재개. 첫 번째 미완료 레시피의 처음부터 다시 실행 (아래 [이어서 실행 (PARTIAL 재개)](#이어서-실행-partial-재개)) |
| [플랜 중단] | 더 진행하지 않음. `PARTIAL`로 확정 (히스토리에 부분 성공 기록) |

```
📋 플랜 실행 중 — 실패

✅ 1. 이력서 작성 — RES-001
❌ 2. 포지션 탐색 — "포지션 조회" 스텝에서 실패 (500)
⬜ 3. 입사지원 — 미실행

[이어서 실행]  [플랜 중단]
```

- **[이어서 실행](PARTIAL 재개)은 실패한 레시피부터 재개**한다(상세: [이어서 실행 (PARTIAL 재개)](#이어서-실행-partial-재개)). 스텝 단위 부분 재개(실패 스텝부터)는 여전히 [2단계 백로그](#2단계-백로그)이며, 재개는 **레시피 단위**로만 한다.

## 사용자 중단 (실행 중)

실행 중 [중단] 버튼으로 사용자가 멈추는 경우. 제안 시점의 [취소]와 구분한다.

- [중단] 클릭 → **확인 모달** 노출: "완료된 N개는 되돌릴 수 없습니다. 중단하시겠습니까?"
- 확인 시: 현재 레시피의 현재 스텝까지 완료 후 중단. 나머지 레시피 미실행.
- 히스토리: "부분 완료"(`PARTIAL` / outcome=STOPPED) 상태로 저장.
- **미실행(PENDING) 레시피는 PENDING으로 보존**한다(실패 처리와 동일 — 재개 시작 지점 판별용).
- 이미 완료된 레시피 결과는 보존한다. **중단 지점부터의 재개([이어서 실행])를 제공**한다(실패와 같은 메커니즘 — 아래 [이어서 실행 (PARTIAL 재개)](#이어서-실행-partial-재개)). 중단된 레시피부터 다시 실행한다.
- 중지/취소는 반드시 API 경유(FE 단독 해제 금지). 상태값·outcome 정의: [messaging.md 상태 해제](../common/messaging.md#상태-해제-취소--중지--완료) · [실행 종료 사유](../common/messaging.md#실행-종료-사유-outcome).

```
📋 플랜 실행 중 — 중단됨

✅ 1. 이력서 작성 — RES-001
⏹️ 2. 포지션 탐색 — 스텝 2/4에서 중단
⬜ 3. 입사지원 — 미실행

[이어서 실행]  [플랜 중단]
```

### [취소](제안) vs [중단](실행 중) 구분

| 버튼 | 시점 | 동작 |
|------|------|------|
| [취소] | 플랜 제안 카드 (실행 전) | 아무것도 실행 안 함. "취소되었습니다" |
| [중단] | 실행 중 | 확인 모달 → 완료분 보존하고 중단 (PARTIAL/STOPPED) |

## 이어서 실행 (PARTIAL 재개)

실패(PARTIAL, 스텝 FAILED로 인한) 또는 사용자 중단(STOPPED)으로 `PARTIAL` 종료된 실행을, **실패/중단 지점부터 이어서** 다시 실행한다. 실패/중단 카드의 [이어서 실행] 버튼이 트리거다.

### 재개 대상 범위

| 종료 사유 | 재개 |
|-----------|------|
| PARTIAL (스텝 FAILED로 중단) | ✅ 가능 |
| STOPPED (사용자 중단) | ✅ 가능 (같은 메커니즘) |
| CANCELLED (사용자 취소) | ❌ 안 함 ("사용자가 물렀음" — 재개 대상 아님) |
| SUCCESS (정상 완료) | ❌ 재개 불필요 |

### 재개 메커니즘 (확정)

1. **재개 시작 지점 = 첫 번째 미완료(FAILED 또는 PENDING) 레시피의 처음부터.** 완료된 앞 레시피(SUCCESS)와 그 결과는 건드리지 않고 그대로 이어받는다. `EXECUTION_RECIPE`를 sequence 순으로 훑어 첫 번째 비-SUCCESS(FAILED/PENDING) 레시피를 찾는다.
2. **레시피 단위 재시도.** 실패한 레시피가 스텝 중간에 죽었어도 그 레시피 **전체를 처음부터** 재시도한다. 스텝 단위 부분 재개(실패 스텝부터)는 하지 않는다 — 외부 부작용 판단이 복잡하므로 레시피 단위가 안전·단순하다([2단계 백로그](#2단계-백로그)).
3. **기존 EXECUTION 재사용 (CONTEXT 보존이 핵심).** 새 EXECUTION을 만들지 않고 **기존 EXECUTION을 RUNNING으로 되돌린다.** 완료된 앞 레시피가 누적한 CONTEXT(🔗 이전 결과)를 그대로 이어받아 재개 레시피의 데이터 매핑에 활용한다.
4. **재개 대상 레시피의 스텝 재생성.** 재개 시작 레시피를 RUNNING으로 전이하며 그 레시피의 스텝을 새로 생성한다(그 레시피를 처음부터). 이후는 [실행 계약](#실행-계약-be-오케스트레이션--중대)의 일반 오케스트레이션(reportStep 기반 순차 전이)을 그대로 탄다.

> ⚠️ **중복 외부 생성 주의(레시피 단위 재시도의 트레이드오프)**: 실패한 레시피가 스텝 3개 중 2개까지 외부 서버에 데이터를 만든 뒤 죽었다면, 레시피 **전체**를 재시도하므로 그 2개 스텝이 **다시 호출되어 중복 생성**될 수 있다(멱등하지 않은 API의 경우). 이는 "레시피 단위 재시도"를 택한 대가이며, 스텝 단위 부분 재개(실패 스텝부터)로 해결할 문제이나 외부 부작용 판단이 복잡해 [2단계 백로그](#2단계-백로그)로 둔다. 사용자에게 [이어서 실행] 시 이 가능성을 안내한다(재개 확인). 완료된 **앞 레시피**(SUCCESS)는 재실행하지 않으므로 중복되지 않는다 — 중복 위험은 재개 시작 레시피 1개 내부에 한정된다.

```
PARTIAL 종료 상태:
✅ 1. 이력서 작성 (SUCCESS)  — CONTEXT 누적됨 (이어받음)
❌ 2. 포지션 탐색 (FAILED)   — 재개 시작 지점 (처음부터 재시도)
⬜ 3. 입사지원 (PENDING)     — 이어서 실행

[이어서 실행] →
    기존 EXECUTION을 RUNNING으로 되돌림 (CONTEXT 보존)
    → 레시피 2(포지션 탐색)를 RUNNING 전이 + 스텝 재생성
    → 레시피 2 완료 시 레시피 3으로 일반 전이
    → 전체 완료 시 SUCCESS 확정
```

### API / 트리거

- **신규 엔드포인트**: `POST /api/v1/executions/{executionId}/resume`
- 실패/중단 카드의 **[이어서 실행]** 버튼 → resume 호출 → 러너 구동.
- resume 시 **대화방 락을 다시 잡는다.** 이미 처리 중이면 `409`(대화방 단위 락, 동시 요청 불가 — [execution.md 실행 중 입력 제한](execution.md#실행-중-입력-제한)).
- 락 획득 후 `session_status: executing`로 재전이하고, **새 PROGRESS 메시지를 발행**해 재개 진행을 표시한다(기존 PROGRESS와 별개 메시지).
- 재개 대상이 아닌 실행(SUCCESS/CANCELLED/RUNNING)에 resume가 오면 거부한다(400).
- **삭제된 대화의 실행 재개 불가**: 히스토리는 USER_ID 독립이라 삭제 대화의 실행도 히스토리 전체 페이지에 보이지만, resume는 대화방 락/PROGRESS 발행이 전제이므로 **연결된 대화방이 소프트 삭제된(또는 없는) 실행은 재개를 거부**한다(안내: "재개하려면 대화가 필요합니다"). 재실행은 새 대화에서 새 발화로. (연결 대화가 살아있는 실행만 [이어서 실행] 노출.)

### 안 하는 것 (백로그 유지)

- 스텝 단위 부분 재개(실패 스텝부터). 레시피 단위 재시도만 한다.
- 재개 중 레시피 추가/제거([2단계 백로그](#2단계-백로그)).

## 결과 표시

- **결과 카드**: 레시피별 요약 + 상세 보기(사이드 패널 연결은 프로토타입 후속).
- 완료 시 RESULT 메시지 발행([messaging.md RESULT](../common/messaging.md#result-실행-결과-블록)).
- **추정 실행 시간은 표시하지 않는다.** 학습/개인화 기반 예측은 백로그.

---

## 히스토리 표시

```
히스토리:
  09/16 14:30 | 📋 플랜: 입사지원 (3건)     | ✅ 성공 | 12.5s
    └ 이력서 작성 ✅
    └ 포지션 탐색 ✅
    └ 입사지원 ✅
  09/16 14:00 | 📄 회원가입                 | ✅ 성공 | 2.1s
  09/16 13:30 | 📄 공고 생성                | ❌ 실패 | 0.5s
```

- 플랜(N≥2): **묶음으로** 표시. 펼치면 개별 레시피 결과 확인 가능.
- 단일 레시피(N=1): 독립 단건으로 표시.

---

## 저장 정책

- **플랜 자체는 저장하지 않음** (1회성).
- 플랜 내 각 레시피의 실행 결과는 정상적으로 히스토리에 저장됨(묶음).

## AI 플랜 제안 기준

- AI가 매번 추론 (선행 레시피 메타 정의 없음).
- 단일 레시피로 처리 가능하면 → `execute_recipe`(바로 단일 실행).
- 결과 의존이 있는 순차 조합이 필요하다고 판단하면 → `propose_plan`(rationale 필수).
- `recipeIds`가 1개로 귀결되면 BE가 `execute_recipe`로 폴백([plan-proposal.md](../chat/scenarios/plan-proposal.md)).
